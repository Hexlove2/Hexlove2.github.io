Key takeaways

  1. Both detectors end with a plain top-k instead of NMS. They avoid duplicates because training gives every object exactly one positive prediction: Hungarian matching in RT-DETR, task-aligned assignment with k = 1 in YOLO26.
  2. YOLO26 trains two heads on the same features: a one-to-many head (10 positives per object) that shapes the backbone, and a one-to-one head (1 positive) that is the only one shipped. On my test image the first fires 48 times, the second 5 times, once per object.
  3. RT-DETR makes a DETR real-time by running self-attention only on the 400 tokens of the 20×20 map, using the 300 best encoder tokens as queries, and letting each query read just 96 sampled points per decoder layer.
  4. On the published T4 numbers YOLO26 is ahead at every accuracy level. At equal accuracy it also ran 1.7× faster on my laptop’s CPU and 3.3× faster through CoreML. RT-DETR’s strengths are structural: a set-prediction head whose depth you can cut at inference, and a design that newer DETRs keep building on.

Every object detector has to turn an image into a set: an unknown number of boxes, each with a class and a score, and no object reported twice. For most of the last decade, real-time detectors handled the “no object twice” part with a patch. They predicted thousands of overlapping boxes and then deleted the extras with a hand-written algorithm called non-maximum suppression (NMS).

This post is about two detectors that removed the patch, in opposite ways.

  • RT-DETR (Baidu, CVPR 2024) is the first real-time member of the DETR family. It treats detection as set prediction from the start: 300 queries each claim at most one object, and the training loss enforces it with a one-to-one matching.
  • YOLO26 (Ultralytics, 2026) keeps the classic dense CNN, which makes a prediction at every cell of a grid, and adds a second head that learns to fire exactly once per object. It is the newest model in the Ultralytics library.

Both end with nothing more than a top-k. And both have to solve the same sub-problems along the way: how to feed an image in, how to look at several scales at once, how to turn features into boxes, and how to decide during training which prediction should have found which object. Following one image through both pipelines is the best way I know to understand them, so that is what this post does, from pixels to deployment, before a side-by-side comparison.

As in the ResNet post, I checked what I could on my own machine. Every code snippet below produces the same tensors as the Ultralytics implementation (version 8.4.46), and every number I describe as measured comes from the released YOLO26 and RT-DETR-L weights, run on one test photo: an 810×1080 street scene with a bus and four people.

Why NMS had to go

A dense detector predicts something at every cell of a feature grid, and neighboring cells look at almost the same pixels. When an object is there, a whole cluster of cells fires, each proposing a slightly different box. Training even asks for it: from YOLOv8 to YOLO11, the ten best-placed cells for every object are all trained as positives, so the model learns to predict about ten boxes per object.

NMS cleans up afterwards, and it is short enough to write out in full:

python
import torch
from torchvision.ops import box_iou


def nms(boxes, scores, iou_thr=0.7):
    order = scores.argsort(descending=True)
    keep = []
    while order.numel():
        i, order = order[0], order[1:]
        keep.append(i)  # the best remaining box wins
        iou = box_iou(boxes[i, None], boxes[order])[0]
        order = order[iou <= iou_thr]  # drop everything that overlaps it too much
    return torch.stack(keep)

It returns exactly what torchvision.ops.nms returns. Detectors run it per class: a cat box should not delete an overlapping dog box. There are three problems with it.

One threshold cannot fit every scene. NMS cannot tell a duplicate from a second object that happens to overlap the first. Two people standing close together look exactly like one person detected twice. Try it:

It costs time, and the cost depends on the image. The loop runs once per kept box and compares it with everything left, so the time grows with the number of boxes that pass the score threshold. The RT-DETR paper measured YOLOv8-L with TensorRT’s NMS on a T4 GPU:

NMS setting (YOLOv8-L, COCO val2017) AP NMS time
IoU 0.5, score 0.001 52.1% 2.24 ms
IoU 0.6, score 0.001 52.6% 2.29 ms
IoU 0.7, score 0.001 52.9% 2.36 ms
IoU 0.8, score 0.001 52.8% 2.46 ms
IoU 0.7, score 0.01 52.4% 1.73 ms
IoU 0.7, score 0.05 51.2% 1.06 ms

Source: Table 1 of the RT-DETR paper. Only the time of the NMS kernel itself.

Two milliseconds sounds small until you compare it with the network: YOLO26n runs in 1.7 ms on the same GPU. And to save that time you turn a knob that also costs accuracy.

It lives outside the network. NMS is a loop whose length depends on the data. An exported model either calls a vendor plugin, such as TensorRT’s EfficientNMS, or hands its raw tensors to CPU code after the network has finished. Every runtime does this a little differently, and many NPUs (the AI accelerators in phones and edge devices) and INT8 pipelines cannot run it at all. The model you benchmark and the system you ship are not the same thing.

The fix, in both detectors, is to make the network itself responsible for not repeating itself. That only works if training never rewards a second box for an object that already has one. This idea runs through the rest of the post.

Getting pixels in

Both models take a 3×640×640 tensor of RGB values between 0 and 1. Neither subtracts an ImageNet mean or divides by a standard deviation: the first convolution and its batch norm learn whatever scaling they need.

YOLO26 letterboxes. It scales the image so that the longer side becomes 640, keeps the aspect ratio, and pads the rest with gray:

python
import cv2
import numpy as np


def letterbox(img, size=640, pad_value=114):
    h, w = img.shape[:2]
    r = min(size / h, size / w)  # one scale for both axes keeps the aspect ratio
    nw, nh = round(w * r), round(h * r)
    if (nw, nh) != (w, h):
        img = cv2.resize(img, (nw, nh), interpolation=cv2.INTER_LINEAR)
    dw, dh = (size - nw) / 2, (size - nh) / 2  # split padding between both sides
    top, bottom = round(dh - 0.1), round(dh + 0.1)  # odd pixel: bottom/right
    left, right = round(dw - 0.1), round(dw + 0.1)
    img = cv2.copyMakeBorder(
        img, top, bottom, left, right, cv2.BORDER_CONSTANT, value=(pad_value,) * 3
    )
    return img, r, (left, top)


def to_tensor(img):
    # OpenCV gives BGR in HWC order; the model wants RGB in CHW order
    x = np.ascontiguousarray(img[..., ::-1].transpose(2, 0, 1))
    return torch.from_numpy(x).float().div(255)[None]  # to [0, 1], add batch dim

On my test photo this gives a scale of 0.593 and 80-pixel gray bands on the left and right, and the result is pixel-for-pixel identical to Ultralytics’ LetterBox. A few details are worth knowing:

  • Why keep the aspect ratio? A squeezed person is a different shape. If inference squeezed images differently from training, the network would see shapes it never learned.
  • Why gray 114? Any constant works as long as training used the same one. Mid-gray is close to the average pixel, so the padding looks like “nothing” to the first layers.
  • Keep r and (left, top). Boxes come out in the 640×640 frame, and you map them back to the photo with xphoto=(x−left)/r.
  • In Python you get a smaller input. model.predict pads only up to a multiple of 32 by default (“rectangular inference”), so my photo becomes 480×640 instead of 640×640. That saves 25% of the pixels. Exported models usually take the fixed square.

RT-DETR simply resizes. Both the original implementation and Ultralytics stretch every image to 640×640 without keeping the aspect ratio, in training and inference alike. (Ultralytics calls it LetterBox(scale_fill=True); I checked that it is exactly cv2.resize.) The boxes come out normalized to [0, 1], so mapping them back is a multiplication by the photo’s width and height. A fixed square input also means the encoder always sees the same 20×20 grid of tokens, which keeps its position encoding simple.

Backbones and the 8,400-cell grid

A detector needs two things from its features: what is there, which deep layers know, and where exactly it is, which shallow layers know better. Objects also come in every size. So both detectors take three feature maps from a CNN backbone, at strides 8, 16 and 32. For a 640×640 input those are grids of 80×80, 40×40 and 20×20 cells:

802+402+202=6,400+1,600+400=8,400.

A cell on the stride-8 map covers 8×8 input pixels and is good for small objects; a cell on the stride-32 map covers 32×32 pixels and sees enough context for large ones.

YOLO26’s backbone is a plain stack of CNN blocks (from yolo26.yaml): stride-2 3×3 convolutions do all the downsampling, and C3k2 blocks sit between them. A C3k2 block is CSP-style: it splits the channels, sends one part through a few residual bottlenecks (the blocks from the ResNet post) and concatenates the parts again, which keeps cost low and gradients short. At the end come two blocks that widen the view of the 20×20 map. SPPF chains three 5×5 max-pools and concatenates their outputs, which pools over 5, 9 and 13 cells at once. C2PSA adds a small self-attention block. Note where that attention sits: only on the coarsest map. RT-DETR makes the same choice, for the same reason.

RT-DETR’s backbone is ResNet-18, 34, 50 or 101 in the paper, in the “vd” variant from the Bag of Tricks paper: a stem of three 3×3 convolutions instead of one 7×7, and the average-pooled shortcut (ResNet-D) described in the ResNet post. The rtdetr-l and rtdetr-x weights that Ultralytics distributes use HGNetv2 instead, a GPU-friendly CNN from Baidu. Either way, the outputs at strides 8, 16 and 32 go on to the next stage.

The grid itself is a few lines. Ultralytics calls these points “anchors”, but there are no anchor boxes in either model: each point predicts one box directly.

python
def make_anchors(img_size=640, strides=(8, 16, 32)):
    points, stride_of = [], []
    for s in strides:
        n = img_size // s  # 80, 40, 20 cells per side
        c = (torch.arange(n) + 0.5) * s  # cell centers in input pixels
        y, x = torch.meshgrid(c, c, indexing="ij")
        points.append(torch.stack([x, y], -1).view(-1, 2))  # row-major order
        stride_of.append(torch.full((n * n, 1), float(s)))
    return torch.cat(points), torch.cat(stride_of)  # (8400, 2), (8400, 1)
  • + 0.5 puts each point at the center of its cell, so the first point sits at pixel 4, not on the image border.
  • Row-major order matches how the head flattens its (B, C, H, W) outputs, so prediction number i belongs to point number i.
  • RT-DETR builds the same grid in normalized coordinates and gives every cell an initial box of 5%, 10% or 20% of the image (twice as big on each coarser level). That box is where its queries start from, as we’ll see.

Mixing scales: PAN vs. the hybrid encoder

The 80×80 map knows where the edges are but not what they belong to; the 20×20 map knows what is in the image but only roughly where. The neck lets each level borrow from the others before anything is predicted.

YOLO26 uses a PAN. A top-down path upsamples the 20×20 map, concatenates it with the 40×40 map and mixes them with a C3k2 block, then does the same into the 80×80 map. A bottom-up path then works its way back from 80×80 to 20×20 with stride-2 convolutions. After both passes, every output level has seen every input level. Everything is convolutions, which every runtime and quantizer handles well.

RT-DETR uses a hybrid encoder. Earlier DETRs ran their Transformer encoder over the tokens of all levels together: 8,400 tokens for a 640×640 image, and many more at the 800×1333 resolution they usually used. Even with Deformable DETR’s cheaper sampled attention, that encoder takes 49% of the model’s GFLOPs while contributing only 11% of its AP (a figure the RT-DETR paper cites from an earlier study). The paper’s key observation is that most of that work is wasted. Self-attention is good at relating concepts to each other (“this wheel belongs to that bus”), and only the deepest map contains concepts. Attention among the low-level edge features of the 80×80 map adds cost, not understanding. So the encoder splits into two parts:

  • AIFI (attention-based intra-scale feature interaction): one Transformer encoder layer with 8 heads, run on the 20×20 map only. That is 400 tokens.
  • CCFF (CNN-based cross-scale feature fusion): a PAN-like CNN that fuses the result back into the 40×40 and 80×80 maps, top-down and then bottom-up, using small RepVGG-style fusion blocks.

The paper’s ablation walks from a DETR with no encoder to this design (ResNet-50, shorter training schedule):

Variant What the encoder does AP Latency
A Nothing (baseline) 43.0% 7.2 ms
B Transformer layer on each level separately 44.9% 11.1 ms
C One Transformer over all levels together 45.6% 13.3 ms
D Attention per level, then CNN fusion across levels 46.4% 12.2 ms
DS5 Same, but attention on S5 only 46.8% 7.9 ms
E DS5 with better fusion blocks: AIFI + CCFF 47.9% 9.3 ms

Source: Table 3 of the RT-DETR paper.

The jump from D to DS5 is the headline: dropping attention on the two finer maps made the encoder 35% faster and more accurate.

AIFI itself is an ordinary post-norm Transformer encoder layer. The only detail worth writing out is the position encoding, since attention on its own does not know where a token is:

python
from torch import nn


def sincos_2d(w, h, dim=256, temperature=10000.0):
    grid_w = torch.arange(w, dtype=torch.float32)
    grid_h = torch.arange(h, dtype=torch.float32)
    gw, gh = torch.meshgrid(grid_w, grid_h, indexing="ij")
    # dim/4 frequencies, from 1 down to 1/10000
    omega = 1.0 / temperature ** (torch.arange(dim // 4) / (dim // 4))
    pw = gw.flatten()[:, None] * omega  # (w*h, dim/4)
    ph = gh.flatten()[:, None] * omega
    # (1, w*h, dim): sin and cos of both coordinates, dim/4 channels each
    return torch.cat([pw.sin(), pw.cos(), ph.sin(), ph.cos()], 1)[None]


class AIFI(nn.Module):
    def __init__(self, c=256, heads=8, ffn=1024):
        super().__init__()
        self.attn = nn.MultiheadAttention(c, heads, batch_first=True)
        self.ffn = nn.Sequential(nn.Linear(c, ffn), nn.GELU(), nn.Linear(ffn, c))
        self.norm1, self.norm2 = nn.LayerNorm(c), nn.LayerNorm(c)

    def forward(self, x):  # x: (B, 256, 20, 20), S5 after a 1x1 projection
        b, c, h, w = x.shape
        t = x.flatten(2).transpose(1, 2)  # (B, 400, 256): one token per cell
        # position goes into queries and keys, not into values
        q = k = t + sincos_2d(w, h, c).to(t)
        t = self.norm1(t + self.attn(q, k, t)[0])  # post-norm, like the original
        t = self.norm2(t + self.ffn(t))
        return t.transpose(1, 2).reshape(b, c, h, w)  # back to a feature map

With the weights copied over from rtdetr-l.pt, this module reproduces Ultralytics’ AIFI output on my test image. The sine–cosine encoding uses a quarter of the 256 channels per function and axis, with frequencies from 1 down to 1/10,000, so nearby cells get similar codes and distant ones different codes. Nothing about it is learned.1

The YOLO26 head: dense, direct, doubled

At each of the 8,400 points, the head predicts two things:

  • 80 class logits, one per COCO class, each with its own sigmoid rather than a softmax across classes. That way a point can say “nothing here” by keeping all 80 low.
  • 4 distances, l, t, r, b, from the point to the left, top, right and bottom sides of the box, in units of the stride.

Each pyramid level has its own two small branches: three convolutions for the box, and two depthwise-separable convolution pairs plus a 1×1 convolution for the classes. Decoding the box is a subtraction and an addition:

python
def decode(ltrb, points, stride_of):
    ltrb = ltrb * stride_of  # the head predicts distances in units of its stride
    x1y1 = points - ltrb[:, :2]
    x2y2 = points + ltrb[:, 2:]
    return torch.cat([x1y1, x2y2], -1)  # (8400, 4)

Measuring in strides keeps the targets in the same numeric range on every level: a large object on the 20×20 map is a few cells wide, and so is a small object on the 80×80 map. Feeding the head’s raw output through this function gives the boxes the model itself produces.

Why DFL is gone

From YOLOv8 to YOLO11, each of the four distances was not one number but a distribution over 16 bins (Distribution Focal Loss, from the GFL paper). The decoded distance is the expected bin:

d=∑i=015i⋅softmax⁡(z)i.

The idea is elegant: an uncertain edge, like the back of a partly hidden car, can spread its probability over several bins. But it has costs, and YOLO26 decided they were not worth paying.

  • Size. 64 outputs per point instead of 4. The YOLO26 paper reports that removing DFL alone takes YOLO11n from 2.6 M parameters and 6.5 GFLOPs to 2.3 M and 5.2 GFLOPs: 12% and 20% less.
  • Range. A distance cannot exceed 15 bins: 120 pixels on the stride-8 map and 480 pixels on the stride-32 map, per side. At 640×640 that rarely matters; at 1280×1280 a large object can be cut short.
  • Export. A softmax over bins followed by an expectation is one more unusual operation for INT8 quantizers and NPU compilers.

YOLO26 sets reg_max=1 in its config: the DFL module becomes nn.Identity and each side is one plain number with no limit. In the paper’s step-by-step ablation this cost 0.6 AP (47.0% → 46.4% for the small model), which the training changes later in this post win back.

Two heads, one shipped

YOLO26’s head has a second copy of both branches, the one-to-one head. It reads the same neck features, but detached from the graph. Simplified from Ultralytics’ Detect.forward:

python
def forward(self, feats):
    one2many = self.forward_head(feats, self.cv2, self.cv3)
    detached = [f.detach() for f in feats]
    one2one = self.forward_head(detached, self.one2one_cv2, self.one2one_cv3)
    if self.training:
        return {"one2many": one2many, "one2one": one2one}  # both get a loss
    return self.postprocess(self.inference(one2one))  # only the one-to-one head

The two heads get different training targets (more on that in the training section). The one-to-many head is trained to fire about ten times per object, like YOLO11. The one-to-one head is trained to fire exactly once. Because of the detach(), only the one-to-many loss shapes the backbone and neck. The one-to-one head is a pair of small branches that learn to pick one cell from features that were trained with rich, forgiving supervision. That is my reading of why the code detaches: the one-to-one targets are harsh, since a cell right next to the chosen one is trained as background even though it sees almost the same pixels, and those gradients would otherwise push neighboring features apart.

Here is the result on my test photo. I decoded both heads of yolo26n.pt:

The one-to-many head has 48 boxes above a score of 0.25: 10, 10, 9, 9 and 10 around the five objects. NMS reduces them to 5. The one-to-one head has exactly 5 points above 0.25 to begin with. When you export the model, the one-to-many branches are simply dropped (I checked: the exported ONNX file contains only the one-to-one weights). YOLO26n has 2.57 M parameters during training and 2.42 M at inference, the 2.4 M in the paper’s table.

The RT-DETR decoder: 300 queries, six refinements

The original DETR started from 100 learned query vectors that knew nothing about the image. Each one had to find “its” object by attending to the whole feature map through six decoder layers, and training took 500 epochs. RT-DETR’s queries start from the image instead.

Query selection

After the encoder, the three maps are flattened into one sequence of 8,400 tokens with 256 channels each. A small head scores every token for all 80 classes and predicts a box for it, as an offset from the token’s initial box. The 300 tokens with the highest class score become the queries: their features are the queries’ content, and their boxes are the starting reference boxes.

python
def select_queries(
    memory, anchors, valid, enc_output, enc_score_head, enc_bbox_head, k=300
):
    """memory: (B, N, 256), the flattened tokens of all three levels.
    anchors: (1, N, 4), each token's initial box in logit space."""
    feats = enc_output(memory * valid)  # Linear + LayerNorm; border tokens zeroed
    logits = enc_score_head(feats)  # (B, N, 80): a class score for every token
    idx = logits.max(-1).values.topk(k, dim=1).indices  # the k best tokens
    index = idx[..., None].expand(-1, -1, feats.shape[-1])
    top = torch.gather(feats, 1, index)  # (B, k, 256)
    ref = enc_bbox_head(top) + anchors[0, idx]  # anchor + offset, in logit space
    return top, ref, idx  # content queries, reference boxes, token ids

On the real encoder output of rtdetr-l.pt, this returns exactly the queries and reference boxes of Ultralytics’ _get_decoder_input. Three details:

  • Boxes live in logit space. The initial boxes are stored as σ−1(b), the inverse sigmoid. Adding an offset there and applying a sigmoid later keeps every coordinate between 0 and 1, however large the offset is.
  • The valid mask disables tokens whose initial box would be centered within 1% of the image border. Here that is the outermost ring of the 80×80 map: 8,084 of the 8,400 tokens remain.
  • The scores are trained to mean “well localized”. During training, the classification target of a token is the IoU of its box, not 1 (the varifocal loss, below). So picking the highest scores picks tokens with good boxes. The paper calls this uncertainty-minimal query selection, and it adds 0.8 AP.

Six layers of refinement

Each decoder layer updates all 300 queries in three steps:

  1. Self-attention between the queries, so they can see what the others are claiming.
  2. Multi-scale deformable cross-attention. Instead of attending to all 8,400 tokens, each query predicts 4 sampling points around its reference box for each of 8 heads and 3 levels, and reads the features there by bilinear interpolation: 96 samples per query.
  3. A feed-forward network.

Then a box head predicts a correction in logit space, and the corrected box becomes the reference for the next layer:

python
def inverse_sigmoid(x, eps=1e-5):
    x = x.clamp(0, 1)
    return torch.log(x.clamp(min=eps) / (1 - x).clamp(min=eps))


def decode_queries(
    decoder, query, ref, memory, shapes, bbox_heads, score_heads, pos_mlp
):
    boxes, scores = [], []
    ref = ref.sigmoid()  # (B, k, 4): cx, cy, w, h in [0, 1]
    for layer, box_head, cls_head in zip(decoder.layers, bbox_heads, score_heads):
        # self-attention, deformable cross-attention, FFN
        query = layer(query, ref, memory, shapes, None, None, pos_mlp(ref))
        # refine: add a correction in logit space, then squash back to [0, 1]
        ref = torch.sigmoid(box_head(query) + inverse_sigmoid(ref))
        boxes.append(ref)
        scores.append(cls_head(query))  # class logits
    return boxes, scores

Every layer has its own box and class head, and every layer’s output is trained to be a final answer. The boxes after the sixth layer are the model’s output, identical to Ultralytics’. One training detail from DINO doesn’t show in this inference version: during training, the reference passed to the next layer is detached, but the loss of layer i is computed from the undetached box of layer i−1 plus layer i’s correction. So each layer’s loss also improves the layer before it. DINO calls this “look forward twice”.

Here is what that looks like on my test photo:

Three things surprised me.

  • The queries came from only two maps. Of the 300 tokens selected, 209 came from the 80×80 map, 91 from the 20×20 map and none from the 40×40 map. All five detections came from the 20×20 map, which makes sense for objects this large.
  • The starting boxes were already good. The proposals from query selection overlap the final boxes with an IoU of 0.94 to 0.97. The six layers mostly polish: the bus moves the most, from 0.94 to 1. The scores move too: the person cut off at the left edge goes from 0.76 to 0.86.
  • There were no duplicates to remove, even at stage 0. For every object, exactly one query scored above 0.3; the runner-up near each object scored about 0.07. On this photo, the “one box per object” behavior was already there before any query had attended to another, so it came from the one-to-one training of the scoring head, not from the decoder’s self-attention. On a crowded scene the decoder probably has more to do.

Because every layer is trained to give a final answer, you can also stop early. The paper does exactly that: RT-DETR-R50 with only 5 of its 6 decoder layers loses 0.1 AP (53.1% → 53.0%) and saves 0.5 ms (9.3 → 8.8 ms), and the smaller models ship with 3 or 4 layers. In Ultralytics this is the eval_idx argument of RTDETRDecoder. On my photo, the boxes after layer 5 match the final ones with a mean IoU above 0.999.

Getting boxes out

Both models end with a fixed-size set of 300 candidates, so post-processing is sorting and thresholding.

YOLO26 does it inside the network with a two-step top-k:

python
def topk_postprocess(boxes, scores, k=300):
    """boxes (8400, 4) xyxy, scores (8400, 80) after sigmoid.
    Returns (k, 6): x1, y1, x2, y2, score, class."""
    nc = scores.shape[1]
    best = scores.max(1).values.topk(k).indices  # 1) the k most confident points
    conf, flat = scores[best].flatten().topk(k)  # 2) the k best (point, class)
    anchor, cls = best[flat // nc], flat % nc
    return torch.cat([boxes[anchor], conf[:, None], cls[:, None].float()], 1)

This reproduces the model’s own (1, 300, 6) output exactly. The first step narrows 8,400 points down to 300, so the second top-k runs over 24,000 scores instead of 672,000. And because the second step ranks (point, class) pairs, one point can appear twice with two classes when it is unsure between, say, a dog and a cat. Then you keep the rows above a confidence threshold (0.25 by default) and map them back to the photo.

RT-DETR outputs (1, 300, 4 + 80): a normalized cx, cy, w, h box and 80 sigmoid scores per query. Ultralytics keeps each query’s best class:

python
from torchvision.ops import box_convert


def rtdetr_postprocess(y, width, height, conf=0.25):
    boxes, scores = y[0].split((4, y.shape[-1] - 4), dim=-1)  # (300, 4), (300, 80)
    score, cls = scores.max(-1)
    keep = score > conf
    scale = torch.tensor([width, height, width, height])
    xyxy = box_convert(boxes[keep], "cxcywh", "xyxy") * scale
    order = score[keep].argsort(descending=True)
    return torch.cat([xyxy, score[keep, None], cls[keep, None].float()], 1)[order]

On my photo this returns the same nine boxes as RTDETR.predict: the five from Figure 7, plus four low-confidence detections of small things (a “fire hydrant”, a “traffic light” and two “ties”, scored 0.26 to 0.34). None of the nine is a duplicate of another. A fixed number of outputs is also friendly to deployment: there are no dynamic shapes, and the consumer simply reads rows until the score drops below its threshold.

Training YOLO26: who counts as positive

Training a dense detector comes down to one decision per object: which of the 8,400 points should predict it? Those points are the positives; every other point is trained as background. This decision, called label assignment, is exactly where the one-to-many and one-to-one heads differ.

Task-aligned assignment

YOLO26 uses task-aligned assignment (TAL, from the TOOD paper). For each labeled object and each point:

  1. The point is a candidate if it lies inside the object’s box.

  2. Its alignment metric combines how well the point currently classifies the object and how well its box fits:

    t=sα⋅uβ,α=0.5, β=6,

    where s is the point’s predicted score for the object’s class and u is the CIoU of its predicted box with the label box.

  3. The top k candidates by t become positives: k=10 for the one-to-many head.

  4. A point claimed by two objects keeps the one it overlaps most.

  5. For the one-to-one head: k=7, then only the single best one is kept.

  6. Positives don’t get a classification target of 1, but a soft target: t rescaled so that each object’s best point gets the highest IoU among that object’s positives.

The metric uses the model’s own current predictions, so the assignment changes as the model trains, and points that both classify and localize well are the ones rewarded. That alignment is what makes “trust the highest score” a sensible rule, whether the next step is NMS or a top-k. β=6 makes the box quality dominate: a point with IoU 0.9 beats one with IoU 0.8 by a factor of (0.9/0.8)6≈2.

Written out, the whole assigner is about twenty lines. On YOLO26n’s real predictions for my photo it selects exactly the same positives, with exactly the same soft targets, as Ultralytics’ TaskAlignedAssigner, for both heads:

python
from torchvision.ops import complete_box_iou


def task_aligned_assign(
    scores, boxes, points, gt_cls, gt_boxes,
    topk=10, topk2=None, alpha=0.5, beta=6.0,
):
    """scores (A, C) after sigmoid; points (A, 2);
    boxes (A, 4) and gt_boxes (G, 4) as xyxy pixels."""
    # 1) candidates: points inside the label box
    #    (STAL: for this test only, sides under 8 px count as 16 px)
    cx = (gt_boxes[:, 0] + gt_boxes[:, 2]) / 2
    cy = (gt_boxes[:, 1] + gt_boxes[:, 3]) / 2
    w, h = gt_boxes[:, 2] - gt_boxes[:, 0], gt_boxes[:, 3] - gt_boxes[:, 1]
    w, h = torch.where(w < 8, 16, w), torch.where(h < 8, 16, h)
    grown = torch.stack([cx - w / 2, cy - h / 2, cx + w / 2, cy + h / 2], 1)
    past_lt = (points[None] - grown[:, None, :2]).amin(-1) > 1e-9
    before_rb = (grown[:, None, 2:] - points[None]).amin(-1) > 1e-9
    inside = past_lt & before_rb  # (G, A)
    # 2) alignment metric t = s^alpha * u^beta
    iou = complete_box_iou(gt_boxes, boxes).clamp(0) * inside  # (G, A)
    s = scores[:, gt_cls].T * inside  # each point's score for each object's class
    metric = s.pow(alpha) * iou.pow(beta)
    # 3) the top-k points per object
    top = metric.topk(topk, dim=1).indices
    pos = torch.zeros_like(metric).scatter_(1, top, 1.0) * inside
    # 4) a point claimed by several objects keeps the one it overlaps most
    multi = pos.sum(0) > 1
    best_gt = iou[:, multi].argmax(0, keepdim=True)
    pos[:, multi] = torch.zeros_like(pos[:, multi]).scatter_(0, best_gt, 1.0)
    # 5) one-to-one head: keep only the best topk2 of them
    if topk2 is not None:
        best = (metric * pos).topk(topk2, dim=1).indices
        pos *= torch.zeros_like(pos).scatter_(1, best, 1.0)
    # 6) soft targets: rescale t so each object's best point gets its best IoU
    t = metric * pos
    best_iou = (iou * pos).amax(1, keepdim=True)
    t = (t * best_iou / (t.amax(1, keepdim=True) + 1e-9)).amax(0)
    return pos.bool(), t  # (G, A) positives, (A,) soft targets

Both heads use the same metric with the same α and β; only k differs. YOLOv10, where this dual-assignment idea comes from, calls it a consistent matching metric: the one-to-one head is pushed toward the same points that the one-to-many head finds best. In my photo its single positive was always among the one-to-many head’s ten, usually the first or second.

Small objects: STAL

Step 1 has a blind spot. Stride-8 points are 8 pixels apart, so a box smaller than 8 pixels may contain no point at all. Such an object gets no positives and is never trained as an object. YOLO26’s small-target-aware label assignment (STAL) fixes this in the simplest way possible: for the inside test only, any side under 8 pixels counts as 16 pixels. The label itself stays unchanged for the loss. In the paper’s ablation it adds 0.2 AP overall (46.6% → 46.8%), and the paper’s examples show fewer missed tiny objects. I checked it with a 5×6-pixel box placed so that no grid point falls inside it: without STAL it has zero candidates, with STAL it has five, and the assigner turns one of them into a positive, exactly as in Ultralytics.

The losses

Each head gets the same three terms, computed on its own positives:

  • Classification: binary cross-entropy between the predicted scores and the soft targets (zero for background), divided by the sum of the targets. Weight 0.5.
  • Box overlap: 1−CIoU for each positive, weighted by its soft target. Weight 7.5.
  • Box distances: an L1 loss on the four distances, normalized by the image size. It replaces the DFL loss and takes over its slot and its weight, 1.5.

ProgLoss: shifting weight to the head you ship

The two head losses are mixed with weights that change during training:

ℒ=wo2m(e)ℒone-to-many+(1−wo2m(e))ℒone-to-one,

where wo2m falls linearly from 0.8 in the first epoch to 0.1 in the last:

python
def progloss_weights(epoch, epochs, start=0.8, end=0.1):
    """epoch counts from 0. Returns (one-to-many weight, one-to-one weight)."""
    o2m = max(1 - epoch / max(epochs - 1, 1), 0) * (start - end) + end
    return o2m, 1 - o2m

Early on, the dense head dominates and the backbone learns from plenty of positives. Later, the weight moves to the head that will actually run. The paper’s ablation: equal fixed weights reach 46.4 end-to-end AP, this schedule 46.7. There is a side effect that follows from the detach() above: since only the one-to-many loss reaches the backbone, the schedule also shrinks the backbone’s gradients eightfold over training, while the one-to-one head’s grow 4.5×.

MuSGD

YOLO26 trains with MuSGD, which mixes SGD with Muon, an optimizer that became popular for training language models. Muon’s idea fits in two sentences. Write the (momentum-averaged) gradient of a weight matrix as G=UΣV⊤; SGD steps along G, so directions with large singular values dominate the step. Muon steps along UV⊤ instead, the same directions with every singular value set to 1, so every direction moves at the same rate.

An exact SVD at every step would be too slow, so Muon approximates UV⊤ with five Newton–Schulz iterations. Each iteration applies an odd polynomial to the matrix, which acts on every singular value separately: σ↦3.4445σ−4.7750σ3+2.0315σ5. Those coefficients make a small σ grow by a factor of about 3.4 per step and then keep it hovering around 1, roughly between 0.7 and 1.2, instead of converging exactly. Very small singular values don’t make it all the way in five steps, as the figure below shows.

python
def newton_schulz5(G, eps=1e-7):
    X = G.bfloat16()
    # the Frobenius norm bounds the top singular value, so all end up <= 1
    X = X / (X.norm() + eps)
    tall = X.size(0) > X.size(1)
    if tall:
        X = X.T  # iterate on the smaller Gram matrix
    for _ in range(5):
        A = X @ X.T
        B = -4.7750 * A + 2.0315 * A @ A
        # every singular value s becomes 3.4445 s - 4.7750 s^3 + 2.0315 s^5
        X = 3.4445 * X + B @ X
    return X.T if tall else X


@torch.no_grad()
def musgd_update(p, state, lr, momentum=0.9, weight_decay=5e-4, muon=0.2, sgd=1.0):
    g = p.grad
    m = state.setdefault("muon", torch.zeros_like(p))  # momentum buffers
    b = state.setdefault("sgd", torch.zeros_like(p))
    # Muon part: Nesterov momentum, then orthogonalize the update as a matrix
    m.lerp_(g, 1 - momentum)
    # a conv weight (out, in, k, k) is treated as an (out, in*k*k) matrix
    u = g.lerp(m, momentum).view(len(g), -1)
    u = newton_schulz5(u) * max(1, u.size(0) / u.size(1)) ** 0.5
    p.add_(u.view_as(p), alpha=-lr * muon)
    # SGD part: Nesterov SGD with weight decay, on the same tensor
    g = g.add(p, alpha=weight_decay)
    b.mul_(momentum).add_(g)
    p.add_(g.add(b, alpha=momentum), alpha=-lr * sgd)

newton_schulz5 is bit-for-bit identical to Ultralytics’ version, and three steps of musgd_update move a weight exactly like their MuSGD optimizer. Every weight with two or more dimensions gets both updates, 0.2× Muon plus 1.0× SGD; biases and batch-norm parameters get SGD only. To see what Newton–Schulz does to a real gradient, I took one from YOLO26n: the weight of the stride-2 convolution that produces the 20×20 map, after a backward pass on my photo.

Ultralytics picks MuSGD automatically for long runs (more than 10,000 iterations) and AdamW for short fine-tunes. In the paper’s ablation, MuSGD adds 0.4 end-to-end AP (46.7% → 47.1%).

The released YOLO26 models were pretrained on Objects365 for 150 epochs and then fine-tuned on COCO for 245, 70, 80, 60 and 40 epochs (n to x). The paper’s step-by-step ablation, from YOLO11s to YOLO26s, shows where the accuracy comes from:

Training RT-DETR: matching sets, plus denoising

DETR-style training starts from the other end. The model outputs a set of 300 predictions, the labels are a set of objects, and the loss is computed only after finding the best one-to-one pairing between the two (a bipartite matching). Predictions that get no object are trained to say “no object”. Since two predictions can never be matched to the same object, a duplicate is always penalized, and the network learns to report each object once. That is the whole reason DETRs need no NMS.

Hungarian matching

The cost of pairing prediction i with object j mixes class and box terms:

Cij=2Ccls+5‖bi−bj‖1+2(1−GIoU(bi,bj)),

with boxes as normalized cx, cy, w, h. The class term is focal-style: with p the predicted probability of the object’s class, Ccls=0.25(1−p)2(−log⁡p)−0.75p2(−log⁡(1−p)), the cost of saying “yes” minus the cost of saying “no”. It can be negative, and the more confident the prediction, the more negative it gets. The Hungarian algorithm then finds the pairing with the smallest total cost:

python
from scipy.optimize import linear_sum_assignment
from torchvision.ops import generalized_box_iou


def hungarian_match(
    logits, boxes, gt_cls, gt_boxes,
    w_cls=2.0, w_l1=5.0, w_giou=2.0, alpha=0.25, gamma=2.0,
):
    """logits (Q, C); boxes (Q, 4) and gt_boxes (G, 4) as cxcywh in [0, 1].
    Returns the matched query ids, gt ids, and the cost matrix."""
    p = logits.sigmoid()[:, gt_cls]  # (Q, G): probability of each object's class
    pos = alpha * (1 - p) ** gamma * -(p + 1e-8).log()  # cost of saying "yes"
    neg = (1 - alpha) * p**gamma * -(1 - p + 1e-8).log()  # minus the cost of "no"
    l1 = torch.cdist(boxes, gt_boxes, p=1)  # (Q, G)
    pred_xyxy = box_convert(boxes, "cxcywh", "xyxy")
    gt_xyxy = box_convert(gt_boxes, "cxcywh", "xyxy")
    giou = generalized_box_iou(pred_xyxy, gt_xyxy)  # (Q, G)
    cost = w_cls * (pos - neg) + w_l1 * l1 + w_giou * (1 - giou)
    q, g = linear_sum_assignment(cost.numpy())  # Hungarian algorithm, on the CPU
    return torch.as_tensor(q), torch.as_tensor(g), cost

It returns the same pairs as Ultralytics’ HungarianMatcher. The matching is computed without gradients; it only decides which prediction is compared with which object.

The loss: IoU-aware classification

For the matched pairs, RT-DETR uses an L1 loss (weight 5) and a GIoU loss (weight 2) on the boxes. For classification it uses the varifocal loss (VFL), where the target of a matched prediction is not 1 but the IoU of its box with the object:

python
import torch.nn.functional as F


def varifocal_loss(logits, target_iou, is_pos, alpha=0.75, gamma=2.0):
    """target_iou: IoU of each matched prediction with its object, else 0."""
    p = logits.sigmoid()
    # positives are weighted by their IoU, negatives focal-style by alpha * p^gamma
    weight = torch.where(is_pos, target_iou, alpha * p.pow(gamma))
    bce = F.binary_cross_entropy_with_logits(logits, target_iou, reduction="none")
    return (bce * weight).mean(1).sum()

A prediction with a sloppy box is therefore trained to be less confident. That is the same idea as YOLO26’s soft targets, and it is what makes the score a good ranking signal for query selection. (The paper uses α=0.75,γ=2; Ultralytics’ defaults are 0.25 and 1.5. The function matches Ultralytics’ VarifocalLoss with either.)

The loss is applied seven times per image: to the 300 proposals from query selection and to the output of each of the six decoder layers, each with its own matching. That is a lot of supervision for one forward pass, and it is why every layer’s output is usable on its own.

Contrastive denoising

Bipartite matching has a weakness early in training: the same query can be matched to different objects in consecutive iterations, so its target keeps changing. That instability is a big part of why the original DETR needed 500 epochs. DN-DETR and DINO fixed it with denoising queries, and RT-DETR uses them too.

During training only, extra queries are built from noisy copies of the label boxes. Their targets are known by construction, so they need no matching:

  • Positive copies move each edge by less than half the box size, and must reconstruct the original box and class.
  • Negative copies move each edge by between half and one box size, and must predict “no object”. This explicitly teaches the model to reject near-miss boxes, which is exactly what a duplicate looks like.
  • A quarter of the class labels are also swapped for random classes, so the model learns to correct those too.
python
def noisy_boxes(gt, scale=1.0, negative=False):
    """gt: (G, 4) cxcywh in [0, 1]. Positives move each edge by less than
    half the box size; negatives by between 0.5 and 1 times it."""
    xyxy = box_convert(gt, "cxcywh", "xyxy")
    half = (gt[:, 2:] / 2).repeat(1, 2) * scale  # (w/2, h/2, w/2, h/2)
    mag = torch.rand_like(gt) + (1.0 if negative else 0.0)  # [0, 1) or [1, 2)
    sign = torch.randint_like(gt, 0, 2) * 2 - 1
    return box_convert((xyxy + sign * mag * half).clamp(0, 1), "xyxy", "cxcywh")

I sampled 20,000 of each for one box. The positives overlap the original with a median IoU of 0.38 (10th to 90th percentile: 0.21 to 0.55); the negatives with a median of 0.01 (0 to 0.13). So “positive” here does not mean “already close”: the decoder has to learn real corrections.

The number of groups adapts to the batch. The paper sets the “denoising number” to 200: if the busiest image in a batch has 10 objects, that gives 200 / 10 = 20 groups, each holding a positive and a negative copy of every object, so 400 extra queries in total. Ultralytics uses 100 by default.

The rest of the recipe is classic DETR: AdamW with a learning rate of 10⁻⁴ (10⁻⁵ for the ImageNet-pretrained backbone, whose batch norms stay frozen), weight decay 10⁻⁴, 2,000 warm-up steps, gradient clipping at 0.1, an EMA of the weights with decay 0.9999, and 72 epochs on COCO. With Objects365 pretraining, RT-DETR-R18, R50 and R101 reach 49.2%, 55.3% and 56.2% AP.

Deployment

Exporting is the same one-liner for both models in Ultralytics:

python

I ran these exports for YOLO26n, s and m and for RT-DETR-L (ONNX 1.23, ONNX Runtime 1.31) and opened the resulting graphs:

  • The exported models give the same detections as PyTorch: identical boxes, scores within 10⁻⁶.
  • Neither graph contains a NonMaxSuppression node. YOLO26’s graph has two TopK nodes, the two-step top-k from above, now part of the model itself. RT-DETR’s has one TopK (query selection) and 18 GridSample nodes: one per decoder layer and feature level, the sampling step of deformable attention.

So there is no plugin to add and no post-processing that behaves differently on each runtime. What differs is everything else inside:

  • YOLO26 is convolutions plus one small attention block on the 20×20 map. Ultralytics exports it to 19 formats, from TensorRT and CoreML to TFLite, NCNN and Rockchip NPUs, and without DFL there is nothing unusual left in the head to quantize. The published CPU numbers (ONNX on an Intel Xeon at 2.0 GHz) range from 38.9 ms for YOLO26n to 525.8 ms for YOLO26x.
  • RT-DETR relies on layer norms, attention and deformable attention, which reads features at data-dependent locations (GridSample). GPUs and TensorRT handle that well, which is where the paper’s speeds come from. Many CPUs and NPUs are slower at it or don’t support it at all.

My Mac makes the second point concrete. With ONNX Runtime’s CoreML execution provider (Apple’s route to the GPU and Neural Engine, default settings), CoreML accepted 395 of YOLO26m’s 418 nodes; the rest are mostly the final top-k and the matrix products of the small attention block. For RT-DETR-L it accepted only 791 of 998: all 18 GridSample and all 21 LayerNormalization nodes fall back to the CPU, and the graph gets cut into 46 pieces that hand data back and forth. Here are the timings (Apple M3, batch size 1, 640×640, FP32 model, median of 20 runs):

What I find most interesting is how much the two roads converged. YOLO26 took DETR’s central idea, one prediction per object enforced by a one-to-one assignment, and grafted it onto a dense CNN. RT-DETR took YOLO’s CNN neck to make its encoder cheap, and both use an IoU-aware classification target so that the highest score belongs to the best box. Both even restrict self-attention to the coarsest map. My rule of thumb after writing this:

  • On CPUs, NPUs, phones, or under INT8, use YOLO26. It is faster at every size and exports everywhere.
  • For the smallest models, YOLO26 too: RT-DETR starts at 20 M parameters.
  • If you want a transformer decoder to build on, for example for open-vocabulary detection, tracking with queries, or the newer DETR variants, start from RT-DETR. You also get the option to trade decoder layers for speed without retraining.

In Ultralytics, trying both costs one line: YOLO("yolo26n.pt") or RTDETR("rtdetr-l.pt"), with the same predict, val, train and export calls.

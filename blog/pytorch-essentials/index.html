PyTorch Essentials: Teach a Tiny Robot to Learn

Tensors, shapes, autograd, and the training loop—explained through four hands-on labs, a tiny working model, and the bugs you actually need to recognize.

Key takeaways

  1. Every tensor has a shape, dtype, and device. Inspect all three before blaming the model.
  2. backward() computes gradients; the optimizer updates parameters. Gradients accumulate until you clear them.
  3. A training loop is a small experiment: predict, measure error, differentiate, update, and evaluate on unseen data.
  4. eval() changes layer behavior. no_grad() disables gradient recording. Use both for ordinary evaluation.

Imagine a tiny robot working at a packing station. You show it a number, and it must return another number. The secret rule is multiply by two, then add one. The robot does not know the rule. It has two knobs, a weight and a bias, and an impressively bad first guess.

That is enough machinery to understand the core of PyTorch. Bigger models have millions of knobs, but the practical questions remain familiar: What shape is the data? Where did the gradient go? Who actually turns the knobs? Why is the loss suddenly enormous?

We will answer those questions by breaking things on purpose. You need basic Python and the idea of a function; you do not need a GPU. The interactive labs run small JavaScript implementations of the displayed mathematics, not PyTorch in the browser. The Python examples are real PyTorch, with a downloadable experiment at the end.

1. Tensors: numbers with a passport

A tensor is an array of numbers. A scalar has shape [], a vector might have shape [3], and a batch of RGB images often has shape [B, 3, H, W]. The names of those dimensions are your responsibility: PyTorch sees sizes, not “these are the cats.”

Before an operation, check the tensor’s passport:

Property Question Typical mistake
shape How are the numbers arranged? Mixing up channels and image height
dtype What kind of numbers are these? Using integers where floating-point math is needed
device Where do they live? Multiplying CPU inputs by GPU weights
python
import torch

x = torch.tensor([[1, 2, 3], [4, 5, 6]], dtype=torch.float32)
print(x.shape, x.dtype, x.device)
# torch.Size([2, 3]) torch.float32 cpu
print(x.mean(dim=0))  # tensor([2.5000, 3.5000, 4.5000])
print(x.mean(dim=1))  # tensor([2., 5.])

Here dim=0 collapses the row axis, leaving one result per column. Think “which axis disappears?” rather than “does zero mean horizontal?” keepdim=True preserves that axis with size one, which can make subsequent broadcasting easier to reason about. See the official tensor tutorial.

Shape errors that shout—and shape errors that whisper

Matrix multiplication uses @; elementwise multiplication uses *. For two matrices, [m, k] @ [k, n] produces [m, n]: the inner dimensions must agree. A shape error is a helpful refusal. A silent shape expansion can be much worse.

For broadcasting, align dimensions from the right. Matching sizes work; a size of one can expand; absent leading dimensions behave like one. Otherwise the operation fails. This lets [B, C] + [C] add one bias per feature, without manually repeating it. See broadcasting semantics.

But predictions shaped [B, 1] minus targets shaped [B] produce [B, B]. Your program runs while solving the wrong problem. For scalar regression, explicitly align them:

python
prediction = torch.tensor([[1.0], [2.0], [3.0]])
target = torch.tensor([1.0, 2.0, 3.0])
assert (prediction - target).shape == (3, 3)  # the trap
paired_error = prediction - target.unsqueeze(1)
assert paired_error.shape == (3, 1)
assert paired_error.square().mean().item() == 0.0

Reshape is not a shuffle

reshape changes how elements are grouped. permute changes axis order. They do different jobs. If a camera produces [H, W, C], use permute(2, 0, 1) to obtain [C, H, W]; simply reshaping to those sizes scrambles the meaning of the pixels.

python
image_hwc = torch.arange(24).reshape(2, 4, 3)
image_chw = image_hwc.permute(2, 0, 1)
assert image_chw.shape == (3, 2, 4)
assert image_chw[2, 1, 3] == image_hwc[1, 3, 2]
flat = image_chw.reshape(-1)  # can copy when necessary

view requires a compatible memory layout and can fail after a permutation. reshape may return a view or make a copy; use it when either is acceptable. Also prefer squeeze(-1) over a bare squeeze() when removing a known output dimension: the latter can accidentally remove your batch axis when the batch contains one example.

2. Autograd: follow the blame backwards

Our robot predicts yˆ=wx+b. For one example, let x=2, b=1, and the target be 5. With w=1, the prediction is 3 and the squared error is 4.

Which way should the weight move? The chain rule traces responsibility backwards:

L=(yˆ−y)2,∂L∂w=2(yˆ−y)x.

At this starting point, the gradient is 2(3−5)×2=−8. A small increase in the weight lowers the loss locally. The negative sign is a direction cue, not a bad grade.

python
w = torch.tensor(1.0, requires_grad=True)
b = torch.tensor(1.0, requires_grad=True)
prediction = w * 2 + b
loss = (prediction - 5).square()
loss.backward()
print(w.grad.item(), b.grad.item())  # -8.0 -4.0
print(w.item())                     # still 1.0!

During the forward pass, autograd records differentiable operations. backward() traverses that graph and accumulates gradients in the leaf parameters’ .grad fields. It does not update the parameters. An optimizer performs that separate operation. PyTorch rebuilds the graph as you run the next forward pass; normally you do not need retain_graph=True in a training loop. See automatic differentiation.

A scalar loss is convenient because loss.backward() can start from a gradient of one. For a non-scalar output, supply an upstream gradient or reduce it to a scalar deliberately.

WarningDo not cut the wire

loss.item() produces a Python number for logging. loss.detach() creates a tensor disconnected from this gradient history. Neither should replace the original loss used for backpropagation. Wrapping a computed value in torch.tensor(...) also creates a new tensor rather than preserving its history.

3. Training: turn the knobs, then look again

Now give the robot five examples:

x −2 −1 0 1 2
y −3 −1 1 3 5

We start at w=0, b=0 and use mean squared error (MSE). For this particular symmetric dataset, the loss simplifies to

L=2(w−2)2+(b−1)2.

That gives exact gradients ∂L/∂w=4(w−2) and ∂L/∂b=2(b−1). Plain stochastic gradient descent (SGD), here using the entire dataset at once, applies

w←w−η∂L∂w,b←b−η∂L∂b.

The learning rate η controls how far the knobs turn. Try a sensible value, then drive the robot a little too enthusiastically.

With η=0.1, the first update gives w=0.8, b=0.2, and the loss falls from 9 to 3.52. With η=0.6, the weight error gets multiplied by −1.4 each step: it flips sign and grows. We can see the instability before invoking any mysterious “neural network behavior.”

For this exact quadratic, the weight error shrinks only when |1−4η|<1, giving 0<η<0.5. That boundary belongs to this dataset, loss scaling, and optimizer. It is not a universal safe learning rate.

The five lines worth memorizing

python
from torch import nn

x = torch.tensor([[-2.], [-1.], [0.], [1.], [2.]])
y = 2 * x + 1
model = nn.Linear(1, 1)  # one input feature, one output feature
with torch.no_grad():
    model.weight.zero_()
    model.bias.zero_()
optimizer = torch.optim.SGD(model.parameters(), lr=0.1)

model.train()
for _ in range(60):
    optimizer.zero_grad(set_to_none=True)
    prediction = model(x)
    loss = nn.functional.mse_loss(prediction, y)
    loss.backward()
    optimizer.step()

model.eval()
with torch.no_grad():
    print(model(torch.tensor([[3.0]])))  # approximately [[7.0]]

nn.Linear owns learnable parameters, and model.parameters() gives them to the optimizer. nn.Module also lets you compose layers, move them between devices, and save their state. If you write a custom module, put layers in __init__ and the calculation in forward; call model(x) so module hooks work normally. The official quickstart connects these pieces in a classification example.

Notice the order: clear old gradients, predict, measure error, differentiate, update. Forget the clearing step and gradients from earlier updates remain. The checkbox in the lab deliberately demonstrates that bug. Gradient accumulation is useful when intentional—for example, combining several microbatches before one optimizer step—but then the loss scaling and update timing must match that intention.

4. Batches, devices, and a model that can grow

A dataset answers “what is example number i?” A data loader answers “which examples arrive together?” During ordinary training, shuffle the training examples; preserve a separate validation set to check whether learning transfers beyond the examples used for updates.

This self-contained version uses noisy synthetic training data and a clean validation grid. It is a plumbing exercise, not evidence of real-world generalization:

python
import torch
from torch import nn
from torch.utils.data import DataLoader, TensorDataset

torch.manual_seed(7)
device = torch.device(
    "cuda" if torch.cuda.is_available()
    else "mps" if torch.backends.mps.is_available()
    else "cpu"
)
x_train = torch.linspace(-2, 2, 80).unsqueeze(1)
y_train = 2 * x_train + 1 + 0.1 * torch.randn_like(x_train)
loader = DataLoader(TensorDataset(x_train, y_train), batch_size=16, shuffle=True)
model = nn.Sequential(nn.Linear(1, 16), nn.ReLU(), nn.Linear(16, 1)).to(device)
optimizer = torch.optim.Adam(model.parameters(), lr=0.01)

for epoch in range(100):
    model.train()
    total = 0.0
    for xb, yb in loader:
        xb, yb = xb.to(device), yb.to(device)
        optimizer.zero_grad(set_to_none=True)
        prediction = model(xb)
        assert prediction.shape == yb.shape
        loss = nn.functional.mse_loss(prediction, yb)
        loss.backward()
        optimizer.step()
        total += loss.item() * len(xb)
    if epoch % 25 == 0:
        print(epoch, total / len(loader.dataset))

model.eval()
with torch.no_grad():
    xv = torch.linspace(-1.95, 1.95, 40, device=device).unsqueeze(1)
    validation_mse = nn.functional.mse_loss(model(xv), 2 * xv + 1)
    print("validation MSE:", validation_mse.item())

Move the model before creating its optimizer, and move each input and target batch to the same device. A GPU is not automatically faster for a toy dataset: transfer and launch overhead can dominate. The plain CPU version is perfectly adequate here.

The epoch loss above is weighted by batch size. Averaging batch means equally gives a short final batch too much influence. Seeding helps repeat an experiment, but exact equality across devices and PyTorch versions is not guaranteed.

Two switches, two different jobs

Switch Changes Does not do
model.train() Enables training behavior in layers such as Dropout and BatchNorm Start an optimization step
model.eval() Uses evaluation behavior in those layers Disable gradient recording
torch.no_grad() Prevents gradient recording inside its context Switch layer behavior to evaluation

For ordinary validation, use model.eval() and torch.no_grad(). Before the next training phase, call model.train() again. torch.inference_mode() can remove more overhead, but its tensors have extra restrictions when reused with autograd. Start with no_grad() until you need that optimization. See autograd mechanics.

5. Match the loss to the job

The robot predicts a continuous number, so MSE makes sense. A classifier has a different contract. For ordinary single-label classification with C classes, give CrossEntropyLoss raw logits shaped [B, C] and integer class IDs shaped [B], stored as torch.long. Do not apply softmax first.

python
logits = torch.tensor([[2.0, -1.0, 0.5], [-0.5, 0.2, 1.5]], requires_grad=True)
labels = torch.tensor([0, 2], dtype=torch.long)
classification_loss = nn.CrossEntropyLoss()(logits, labels)
classification_loss.backward()
print(logits.argmax(dim=1))  # predicted class IDs: tensor([0, 2])

Cross entropy also supports probability targets with the same shape as the input; those are a different mode from integer class IDs. For independent yes/no labels, BCEWithLogitsLoss is often appropriate, using raw logits and matching floating-point targets. Consult the cross-entropy contract before adapting a training loop.

6. Save the learned knobs

After running the batched example, save its state and reconstruct the same architecture when loading:

python
torch.save(model.state_dict(), "tiny-robot.pt")
restored = nn.Sequential(nn.Linear(1, 16), nn.ReLU(), nn.Linear(16, 1))
restored.load_state_dict(torch.load("tiny-robot.pt", map_location="cpu", weights_only=True))
restored.eval()
with torch.no_grad():
    print(restored(torch.tensor([[1.5]])))  # around 4

A state dictionary contains parameters and persistent buffers, not the model’s Python architecture. For resuming training, also save optimizer state, epoch, and experiment configuration; exact continuation may need RNG and data-order state as well. See the saving and loading guide.

7. A debugging checklist you will actually use

When training behaves strangely, start with the smallest observable thing:

Symptom First inspection
Matrix multiplication fails Write down the shape of both operands and check inner dimensions
Regression runs but learns nonsense Assert prediction and target shapes match exactly
“Expected all tensors to be on the same device” Print input, target, and parameter devices
Loss has no gradient history Look for .item(), .detach(), a new torch.tensor, or no_grad() in the training path
Loss explodes Reduce the learning rate; inspect input scale, finite values, and gradient clearing
GPU memory keeps growing Avoid retaining graph-connected losses or predictions in Python lists; log scalar values
Good training loss, poor validation Inspect leakage, split quality, overfitting, and preprocessing differences
Training works except with one example Look for a bare squeeze() that removed the batch dimension

A useful next experiment is to overfit a single tiny batch. If the model cannot do that, investigate the data, targets, loss, and update path before launching a long run. Once the basic loop is correct, explore mixed precision, profiling, and compilation. Speeding up a broken experiment only gets you the wrong answer sooner.

Reproduce the little robot

Download the runnable PyTorch experiment. It reproduces the five-point training lab, verifies the gradient and broadcasting examples, and checks both the convergent and unstable learning rates. Run it in an environment with PyTorch installed:

bash
python pytorch-essentials.py

The article’s Python blocks and the reference experiment were checked locally with PyTorch 2.11.0. The browser uses JavaScript numbers; PyTorch uses float32 by default, so final digits can differ. All data here are explicitly synthetic. No benchmark or large-model performance claim is being made.

Try one last prediction before you leave: if you double every input without changing the targets, what weight should the robot learn? Change the Python script, run it, and see whether your mental model agrees with the machine.

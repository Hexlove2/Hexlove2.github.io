Key takeaways

  1. YOLO26 的核心是一场反直觉手术：部署期做减法（删 DFL、删 NMS），训练期做加法（双头 + 归一化 L1 + STAL + ProgLoss + MuSGD），把砍掉外挂丢掉的 0.6 mAP 加倍赚了回来。
  2. 翻开 yolo26.yaml 对比 yolo11.yaml，藏着 5 处真实代码改动：SPPF 加残差直连、Neck 三处 C3k2 全员升级 c3k=True、P5 出口 L22 悄悄塞入自注意力 PSABlock、reg_max=1 让检测头参数暴瘦 3 倍，以及 end2end=True 双头训练单头发货。
  3. 源码里最容易踩的 3 个坑：optimizer="auto" 在总步数 ≤ 10,000 时会自动切回 AdamW 并无视你的 lr0；日志里的 dfl_loss 其实是披着旧马甲的 L1 损失；导出 ONNX 的输出已经是 (1, 300, 6)，旧的 84×8400 + NMS 后处理必须全部重写。
  4. 在 i5-14400F + RTX 4060 Ti 实测：TensorRT 10 FP16 下 YOLO26n 端到端 3.80 ms 领先 YOLO11n 的 4.82 ms（快 21%）；密集场景 4,000 候选框时 NMS 暴涨到 46.8 ms，而 YOLO26 始终钉死在 0.046 ms。

如果你用过 YOLOv8 或 YOLO11，第一次听说 YOLO26 可能会翻个白眼：“怎么又出新编号了？不会又是把卷积块换个名字水一波吧？”

这次还真不是。如果只用一句话概括 YOLO26 干了什么：

它在部署期做了一场极狠的减法——把统治了四代 YOLO 的两个祖传外挂（NMS 和 DFL）全砍了；然后在训练期装了四套新引擎，把砍外挂掉下去的精度不仅补回来，还反超了一大截。

架构深潜：把 yolo26.yaml 逐行翻个底朝天

很多文章介绍 YOLO26 只复读“去 NMS、去 DFL”，但如果你真的把 Ultralytics 里的 cfg/models/26/yolo26.yaml 和 cfg/models/11/yolo11.yaml 放在一起 diff，会发现它一共动了 5 处非常精准的手术——其中有 3 处几乎没人提过。

先在下面的 架构 X 光台 里点一遍（默认已把 5 处改动高亮出来，点任意方块看实测张量形状和参数量对比）：

把这 5 刀摊开看，你会立刻明白作者的算盘打得有多精：

隐藏改动 1：SPPF 悄悄加上了残差直连

看 Backbone 第 9 层：YOLO11 写的是 SPPF [1024, 5]，而 YOLO26 改成了 SPPF [1024, 5, 3, True]。点开 ultralytics/nn/modules/block.py 里的 SPPF 源码：

python
class SPPF(nn.Module):
    def __init__(self, c1: int, c2: int, k: int = 5, n: int = 3, shortcut: bool = False):
        super().__init__()
        c_ = c1 // 2
        self.cv1 = Conv(c1, c_, 1, 1, act=False)  # 降维后先不做 SiLU 激活
        self.cv2 = Conv(c_ * (n + 1), c2, 1, 1)
        self.m = nn.MaxPool2d(kernel_size=k, stride=1, padding=k // 2)
        self.n = n
        self.add = shortcut and c1 == c2

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        y = [self.cv1(x)]
        y.extend(self.m(y[-1]) for _ in range(getattr(self, "n", 3)))
        y = self.cv2(torch.cat(y, 1))
        return y + x if getattr(self, "add", False) else y

参数量一个字节都没多，只加了一条 y + x 残差旁路，外加 cv1 关掉激活函数。多尺度最大池化（串 3 次 5×5 池化，等效 5/9/13 感受野）天然会丢掉一部分空间精细信息，残差直连让深层语义和原始特征并存，梯度流更顺滑。

隐藏改动 2 & 3：把砍 DFL 省下的钱，全砸进了 Neck 和第二道自注意力

这是最容易看漏的两行 YAML：

  • Neck 三处融合块（L13 / L16 / L19）全员升级：YOLO11 的 Neck 三个 C3k2 都设了 c3k=False（内部走轻量单 Bottleneck）；YOLO26 把它们全部改成 c3k=True（内部走更深的双层 3×3 C3k）。在 YOLO26n 上这只多了不到 2 万参数，却显著增强了 P3/P4/P5 跨尺度融合能力。
  • 第 22 层 P5 出口塞进第二个自注意力！ 对比一下 L22：
    • YOLO11：[-1, 2, C3k2, [1024, True]]
    • YOLO26：[-1, 1, C3k2, [1024, True, 0.5, True]]

最后一个 True 传给了 C3k2.__init__ 里的 attn: bool = False！一旦 attn=True，C3k2 内部就会实例化 Bottleneck + PSABlock（多头自注意力）。而且 L22 的重复次数从 2 降到 1 控制成本。

为什么要在这里再加一次注意力？ 因为没有 NMS 之后，模型自己必须“心里有数”：画面里到底有几个同类目标、谁离谁近、哪个锚点已经认领了这个物体。在 20×20（只有 400 个空间点）的粗粒度特征图上，Backbone 尾部（L10 C2PSA）做一次全局自注意力，经过 PAN 融合后再在 P5 出口（L22）补一次全局自注意力，计算开销极小，却给了端到端头宝贵的全局视野。

NoteONNX 计算图里的“证据”

我们把 yolo26n.pt 和 yolo11n.pt 都导出成 ONNX 查过算子数量：yolo11n 图里只有 2 个 MatMul（对应 L10 一个 PSABlock），而 yolo26n 里正好有 4 个 MatMul（L10 和 L22 两个 PSABlock 各贡献 2 个矩阵乘）。源码和计算图严丝合缝！

核心手术 4 & 5：删掉 DFL + 双头免 NMS

先动手玩一下检测头实验室，两个 Tab 分别拆解「去 DFL」和「双头实测输出」：

为什么要把用了四代的 DFL 砍掉？

从 YOLOv8 到 YOLO11，网络预测每个锚点到边框四条边的距离 (l, t, r, b) 时，不是直接输出 4 个数，而是给每条边发了 16 个投票箱（reg_max=16），输出 64 个通道，再通过 Softmax 求加权期望：

d=∑i=015i⋅softmax⁡(z)i

DFL 的出发点很优雅（边界模糊时概率可以分散在相邻几个格子里），但在工程落地时暴露了三大硬伤：

  1. 检测头太胖：每个锚点要吐 4 × 16 = 64 个回归通道。实测 yolo11n 单个检测头占了 464,912 参数；YOLO26 把 reg_max 设成 1（self.dfl = nn.Identity()）直接输出 4 个距离，单头参数暴瘦到 154,828——直接缩小 3 倍！ 连双头加起来（309,656）都比 YOLO11 单头还瘦！
  2. 15-stride 硬天花板：16 个箱子最大只能表达 15 × stride 的距离（stride-8 最多 120 px，stride-32 最多 480 px）。640 图里还好，一旦拉到 1280 高分辨率检测大目标，DFL 会直接把超出上限的边截断。
  3. 量化和 NPU 的噩梦：检测头末尾多了一层 Reshape → Softmax → MatMul(0..15)，在 INT8 量化和各类嵌入式 NPU 编译器里非常容易掉点或回退 CPU。删掉之后，YOLO26 的检测头变成了纯干净的卷积，头内部 Softmax 数量归零！

双头训练、单头发货：detach() 和两步 TopK 的精妙配合

来看 ultralytics/nn/modules/head.py 里 Detect 最精华的几十行源码（已精简掉与检测无关的分支）：

python
class Detect(nn.Module):
    def forward(self, x):
        # 1) one-to-many 辅助头：正常连在计算图上，负责把梯度传回 Backbone 和 Neck
        preds = self.forward_head(x, **self.one2many)
        if self.end2end:
            # 2) one-to-one 端到端头：输入特征先 detach()！不把严苛排他梯度回传给骨干
            x_detach = [xi.detach() for xi in x]
            one2one = self.forward_head(x_detach, **self.one2one)
            preds = {"one2many": preds, "one2one": one2one}
        if self.training:
            return preds

        # 3) 推理期只解码 one-to-one 头，并内置两步 Top-300 后处理
        y = self._inference(preds["one2one"] if self.end2end else preds)
        if self.end2end:
            y = self.postprocess(y.permute(0, 2, 1))  # 直接输出 (B, 300, 6)
        return y if self.export else (y, preds)

    def fuse(self) -> None:
        """融合部署时直接删掉 one2many 辅助头！"""
        self.cv2 = self.cv3 = None

这段代码里藏着两个绝妙的工程决策：

  • 为什么要 x_detach = [xi.detach() for xi in x]？ one2one 头的训练极其残酷——一个物体身上明明覆盖了几十个像素点，只有得分最高的 1 个锚点是正样本，紧挨着它 8 像素之外的邻居全被按着头当成**负样本（背景）**来惩罚。如果不做 detach()，这些互相打架的梯度灌回 Backbone，会把本来该提取相似语义的相邻特征硬生生撕裂。截断之后，Backbone 安安心心吃 one2many（每个物体 10 个正样本）的宽容梯度，而 one2one 头则像一个专职裁判，在稳定特征上学会“只让最准的那个点举手”。
  • 两步 TopK 怎么把 8,400×80 压成 (B, 300, 6)？ 直接对 8400 × 80 = 672,000 个分数做全局 Top-300 太慢了，源码 get_topk_index() 拆成了两步：
    1. 先对每个锚点取 80 类里的最大值，从 8,400 个锚点里挑出最好的 300 个锚点；
    2. 再在这 300 × 80 = 24,000 个分数里挑全局前 300 个 (锚点, 类别) 对（搜索量缩小 28 倍！）。
    3. 顺带一提：如果你推理时传了 agnostic_nms=True，get_topk_index() 会走另一条捷径——每个锚点只允许胜出 1 个类别再取 Top-300，防止同一个位置同时报出“狗 0.6 + 猫 0.5”。

训练流水线：靠哪“四大护法”把精度反超回来？

前面说过，刚把 DFL 从 YOLO11s 身上切下来时，COCO 精度其实是先跌了 0.6 个点（47.0% → 46.4%）。YOLO26 凭什么不但填平了坑，还能在免 NMS 的前提下冲到 47.8%？靠的是训练流水线里的四套组合拳。

护法一：穿了 dfl_loss 旧马甲的归一化 L1 损失

没有 DFL 之后，只靠 CIoU 回归边框坐标在尺度差异大时收敛会慢一拍。打开 ultralytics/utils/loss.py 里的 BboxLoss，你会看到一段让人会心一笑的代码：

python
if self.dfl_loss:
    # YOLO11 走这里：16-bin 交叉熵分布损失
    target_ltrb = bbox2dist(anchor_points, target_bboxes, self.dfl_loss.reg_max - 1)
    loss_dfl = self.dfl_loss(pred_dist[fg_mask].view(-1, self.dfl_loss.reg_max), target_ltrb[fg_mask]) * weight
    loss_dfl = loss_dfl.sum() / target_scores_sum
else:
    # YOLO26 (reg_max=1) 走这里：按图像宽高归一化的直接 L1 距离损失！
    target_ltrb = bbox2dist(anchor_points, target_bboxes) * stride
    target_ltrb[..., 0::2] /= imgsz[1]
    target_ltrb[..., 1::2] /= imgsz[0]
    pred_dist = pred_dist * stride
    pred_dist[..., 0::2] /= imgsz[1]
    pred_dist[..., 1::2] /= imgsz[0]
    loss_dfl = F.l1_loss(pred_dist[fg_mask], target_ltrb[fg_mask], reduction="none").mean(-1, keepdim=True) * weight
    loss_dfl = loss_dfl.sum() / target_scores_sum

三个关键细节直接记住：

  • 终端训练日志里第三列依然叫 dfl_loss，超参数权重依然借用 dfl: 1.5（外加 box: 7.5 的 CIoU 和 cls: 0.5 的 BCE），但实际算的是图像尺寸归一化的 L1 损失。
  • 为什么除以 imgsz？因为去掉 DFL 上限后，不同分辨率下像素距离量级不同，归一化到 [0, 1] 让大小目标和不同 imgsz 都能保持稳定的梯度尺度。

护法二：STAL（小目标感知标签分配）——治好 Stride-8 的“网格失明”

传统的任务对齐分配（TAL）第一步是找候选锚点：只有中心点落进真值框（GT）内部的锚点，才有资格参选正样本。

听起来很合理？但算一笔账就吓一跳：YOLO 最密的 P3 特征图步长也是 8 px，锚点中心每隔 8 个像素才有一个（4, 12, 20, 28…）。如果画面里有一颗 4×4 px 的远景焊点、PCB 元件或航拍车辆，它有近 70% 的概率恰好掉在四个锚点中间的空隙里——结果命中 0 个候选点，整轮训练里这颗小目标彻底白标，一个像素的梯度都拿不到！

YOLO26 的 STAL（Small-Target-Aware Label Assignment） 解法简单粗暴到只有 4 行源码（ultralytics/utils/tal.py）：

python
gt_bboxes_xywh = xyxy2xywh(gt_bboxes)
# 只要宽或高小于最小步长（stride[0] = 8 px），仅在候选筛选阶段把它临时扩成 16 px（stride[1]）！
wh_mask = gt_bboxes_xywh[..., 2:] < self.stride[0]
gt_bboxes_xywh[..., 2:] = torch.where(
    (wh_mask * mask_gt).bool(),
    torch.tensor(self.stride_val, dtype=gt_bboxes_xywh.dtype, device=gt_bboxes_xywh.device),
    gt_bboxes_xywh[..., 2:],
)

注意两点极容易误解的地方：

  1. 高和宽是独立判断的：一根 4×18 px 的细长线缆，只会把宽扩到 16，高维持 18 不动。
  2. 只影响找候选点，绝不篡改回归真值：算 CIoU 和 L1 损失时，依然严格对齐原始的 4×4 px 框，不会把小目标教胖。

WarningSTAL 是一把双刃剑：标注脏框会被放大！

以前你的数据集里如果混进了几个误标的 3×3 px 噪点框，传统 TAL 大概率抓不到锚点，相当于帮你“悄悄滤掉了”。但开了 STAL 之后，任何 < 8 px 的脏框都会 100% 强行分配正样本梯度！用 YOLO26 训自定义工业数据集前，务必写脚本扫一遍极小异常标注。

护法三：ProgLoss（渐进交接）+ 两阶段 topk=7 → topk2=1

训练双头时，如果从头到尾固定给 one2many 和 one2one 一样的权重，前期端到端头在烂特征上瞎学，后期骨干又还在被辅助头拽着乱晃。

看看 ultralytics/utils/loss.py 里的 E2ELoss 源码，短得像一首诗：

python
class E2ELoss:
    def __init__(self, model, loss_fn=v8DetectionLoss):
        self.one2many = loss_fn(model, tal_topk=10)
        self.one2one  = loss_fn(model, tal_topk=7, tal_topk2=1)  # 先选 7 个去冲突，再留 1 个！
        self.o2m = 0.8          # 初始：辅助头占 80%，端到端头占 20%
        self.final_o2m = 0.1    # 末期：辅助头退到 10%，端到端头升到 90%

    def __call__(self, preds, batch):
        loss_o2m = self.one2many.loss(preds["one2many"], batch)
        loss_o2o = self.one2one.loss(preds["one2one"], batch)
        # 反向传播用加权和，但终端进度条只打印 loss_o2o[1]（发货头的真实损失）
        return loss_o2m[0] * self.o2m + loss_o2o[0] * self.o2o, loss_o2o[1]

这里面藏着两个教科书级别的细节：

  1. 为什么 one2one 不直接写 tal_topk=1，而要拐个弯写 tal_topk=7, tal_topk2=1？ 想象两个紧挨着的人，如果两人都只挑自己排第 1 的那个锚点，刚好撞车抢了同一个点，去冲突后其中一个人就会被判成 0 个正样本！先各挑 7 个候选做完多目标冲突仲裁（把撞车的点判给 IoU 更高的那个物体），然后再从各自剩下的候选里取排第 1 的那个（topk2=1），就能优雅避开“撞车饿死”。
  2. ProgLoss 和 detach() 联手产生的神奇副作用：拖动下面的进度条感受一下——随着 w_o2m 从 0.8 线性降到 0.1，由于只有 one2many 会把梯度传进 Backbone，骨干网络的梯度幅度会在训练全程自动缩小 8 倍，同时 one2one 头的梯度放大 4.5 倍，就像教练前期手把手扶着车把，快考试时慢慢松手让你自己冲线！

Important工程提醒：别拿 epochs=10 的极短训来评判 YOLO26！

因为 ProgLoss 的线性衰减直接绑定 self.one2one.hyp.epochs（总轮数），而且最后 10 轮还有 close_mosaic 关拼接精修。如果你为了省事只跑 1015 轮快速试水，ProgLoss 还没完成平稳交接就草草收场了。自定义微调建议至少给到 **50100 epochs**（小数据集也至少 30 轮以上并把 close_mosaic 调小到 5）。

护法四：MuSGD 优化器，以及 99% 的人都会中招的 optimizer="auto" 秘密！

YOLO26 论文最吸睛的亮点之一就是把大模型圈爆火的 Muon 优化器 搬进了目标检测，和传统 SGD 揉成了 MuSGD：

  • 对所有 ≥ 2 维权重矩阵（卷积核 (out, in, k, k) 会先拍扁成 (out, in*k*k) 二维矩阵）：同时吃 0.2 × Muon + 1.0 × SGD 混合更新（weight decay 只加在 SGD 部分）。
  • 对所有 1 维参数（bias、BatchNorm 缩放参数）：走纯 Nesterov SGD。
  • Muon 到底在干嘛？ 普通 SGD 直接顺着梯度矩阵 G=UΣV⊤ 迈步，但真实梯度里前几个最大奇异值往往独占 80%+ 能量，弱方向根本走不动。Muon 希望把所有奇异值拉平到 1（走 UV⊤），为了不做昂贵的 SVD，它在 bfloat16 下只做 5 步五次多项式 Newton–Schulz 迭代：
Xk+1=3.4445Xk−4.7750(XkXk⊤)Xk+2.0315(XkXk⊤)2Xk

但是！！等等！！ 翻开 ultralytics/engine/trainer.py 第 283 行和第 999 行，你会看到一段极其关键的真相：

python
# ultralytics/engine/trainer.py L283 & L999
iterations = math.ceil(len(self.train_loader.dataset) / max(self.batch_size, self.args.nbs)) * self.epochs
...
if name == "auto":
    # 警告：auto 会直接忽略你手动传入的 lr0 和 momentum！
    nc = self.data.get("nc", 10)
    lr_fit = round(0.002 * 5 / (4 + nc), 6)
    name, lr, momentum = ("MuSGD", 0.01, 0.9) if iterations > 10000 else ("AdamW", lr_fit, 0.9)

看懂了吗？！算一下你就惊了：因为分母是 max(batch_size, 64)，如果你在 1,000 张自定义图上训 100 轮，有效迭代步数是 ceil(1000 / 64) × 100 = 1,600 ≤ 10,000——默认的 optimizer="auto" 压根没给你开 MuSGD，而是悄悄切成了 AdamW！

不仅如此，在 build_optimizer 第 1030 行还藏着一行给 MuSGD 微调开的“后门”：一旦启用 MuSGD，正则匹配 (?=.*23)(?=.*cv3)|proto\.semseg（也就是第 23 层检测头的分类分支 cv3 和分割语义分支），学习率会自动乘以 3 倍（lr * 3 = 0.03），帮新初始化的分类头快速追上预训练骨干！

  3. 显式开启 optimizer="MuSGD" 直接反杀！ 同样只跑 20 轮，显式传 optimizer="MuSGD", lr0=0.01（同时激活源码里 Layer 23 cv3 分类头的 3× 学习率 0.03），免 NMS 的 one2one 头一举飙到 80.16%（比 auto 暴涨 +2.31 个点，反超带 NMS 的 YOLO11n！），唯一代价是 5 步 Newton–Schulz 矩阵乘让每轮训练慢约 31%。

Tip自定义数据集调参黄金法则（基于上述实测）

  • 默认先跑 optimizer="auto" + 足够轮数（≥ 50~100 epochs），稳妥且快；
  • 如果你的微调轮数偏短（20~40 轮），或者 val(end2end=False) 明显高出 val(end2end=True) 超过 2 个点：果断拉长 epochs，或者显式试一下 optimizer="MuSGD", lr0=0.01（若极小数据集 <200 张震荡，再把 lr0 降到 0.005）！

这张实测表能帮你破除两个常见误解：

  1. 为什么 PyTorch 原生 GPU 推理有时感觉 YOLO26 没比 YOLO11 快？ 我们在 RTX 4060 Ti 上用 PyTorch eager 模式裸跑 yolo26n 是 19.8 ms vs yolo11n 16.6 ms，因为 YOLO26 融合后多了 22 层小算子（L22 注意力 + 两步 TopK），Python 逐层发射 CUDA kernel 的 CPU 开销占了大头。但只要导出成 TensorRT 10（或 CoreML / OpenVINO）做图融合，yolo26n 前向瞬间压到 3.07 ms，加上近乎为零的后处理（0.74 ms vs YOLO11n 1.99 ms），端到端直接反超快 21.2%！
  2. 官方宣传的“CPU 提速高达 43%”是怎么来的？ 一部分来自去 DFL 后更轻的检测头（我们在 i5-14400F 单线程下仅前向就快了 14.9%，4 线程快 12.3%），另一大块来自彻底砍掉了 CPU 端的转置 + 阈值筛选 + 贪心 NMS 后处理——在低算力 ARM/树莓派/工控 CPU 加上密集目标场景里，NMS 动辄吃掉 10~40 ms，砍掉之后总延迟立竿见影。

全网社区真实评价 & 选型决策指南（不吹不黑）

为了不只听官方一家之言，我们翻遍了 Reddit /r/computervision、Ultralytics GitHub Issues、以及知乎和工业视觉社区近期的真实测评和踩坑反馈，把大家的共识浓缩成“红榜”和“黑榜”：

大家普遍夸的 4 点

  1. 边缘端与 CPU/INT8 落地真香：去掉 DFL 的 Softmax 期望层和外部 NMS 插件后，无论是 TensorRT、OpenVINO、CoreML 还是国产 NPU（RKNN 等），导出链路干净了一大截；而且 INT8 量化后掉点普遍低于 1%，非常适合工控机、Jetson Orin Nano、树莓派和手机端。
  2. 延迟极度稳定，不再看画面“脸色”：工业产线最怕平时 4 ms、突然堆料时 NMS 卡成 40 ms 导致漏拍丢帧（详见站里的 产线 YOLO 计数实战）。固定 (B, 300, 6) 输出彻底消灭了长尾抖动。
  3. 参数效率明显越级：很多实测反馈 YOLO26s/m 在参数量相近甚至更少的情况下，能打平上一代更大档位的模型；配合 STAL，无人机航拍、PCB 焊点、细胞检测等小目标场景召回率肉眼可见地变好。
  4. 多任务体验统一：检测、分割（Segment26）、姿态（Pose26 + RLELoss）、旋转框（OBB26）全部升级到同一套端到端思路，一套 API 吃遍常见工业视觉任务。

社区吐槽和需要警惕的 4 个现实问题

  1. AGPL-3.0 开源协议红线：和 YOLOv8/YOLO11 一样，Ultralytics 主仓库采用 AGPL-3.0。个人学习、科研、开源项目随便用；但如果要把代码打包进闭源商业软件交付给客户，必须考虑购买 Ultralytics 商业授权，或者转向 Apache-2.0 协议的替代方案（如 RT-DETR、RF-DETR、YOLOX 等）。
  2. 极小数据集（< 200 张）开箱即用并不总是自动碾压 YOLO11：GitHub Issues（例如 #23978 一类小样本微调反馈）和 Reddit 都有开发者提到，在极小或标注粗糙的私有数据集上直接换 YOLO26，有时会遇到初期框发飘或指标和调好的 YOLO11 持平的情况——背后原因正是我们前面拆出来的三件事：轮数太短导致 ProgLoss 没过渡完、脏小框被 STAL 放大、或者强行开了高学习率 MuSGD。
  3. 老产线的 C++ 后处理代码不能直接复用：所有基于 (1, 84, 8400) 的祖传解析代码都得改写一次（不过改完之后你会开心，因为代码行数能砍掉一大半）。
  4. 极度重叠遮挡的理论天花板：即使在官方 COCO 基准里，端到端 one2one 头也比同权重的 one2many + NMS 低 0.6 ~ 0.8 mAP。如果你的场景是极度密集人头/货堆重叠且算力极其充裕，记得用 end2end=False 做个 AB 对照再定案。

ProgLoss w_o2m 从 0.8 → 0.1，w_o2o 从 0.2 → 0.9；顺带让骨干梯度末期缩小 8×
tal_topk=7, topk2=1 one-to-one 头先拿 7 候选去多目标冲突，再取第 1 名，防紧邻目标撞车饿死
MuSGD ≥2D 权重吃 0.2×Muon(5步NS) + 1.0×SGD；Layer 23 cv3 分类头自动享 3× 学习率
optimizer="auto" ceil(N / max(bs, 64)) × epochs ≤ 10,000 自动选 AdamW 并无视 lr0，超 1 万才选 MuSGD
end2end=False 验证或推理时切回 one-to-many + NMS 头的正确参数（不是 nms=True！）
Windows Intel CPU 混合大小核跑 ONNXRuntime 务必设 intra_op_num_threads=4（P 核数），避免线程互掐慢 6 倍

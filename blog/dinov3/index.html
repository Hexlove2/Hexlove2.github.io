Key takeaways

  1. DINOv3 learns without labels by making a student network agree with a slowly moving teacher on different crops of the same image (DINO), on masked patches (iBOT), and, new in v3, on the structure of patch similarities (Gram anchoring).
  2. Its patch features are the product: frozen, they already separate objects and parts, and they stay clean at high resolution. Most uses are a light head or a nearest-neighbor search on top of them.
  3. Almost every use is one of a few patterns: the CLS token for classification and retrieval, patch features for segmentation, correspondence and detection, nearest neighbors over patches for defect detection. The head on top is often a single linear layer or a k-NN search.
  4. For memory-bank defect detection on MVTec AD, resolution and layer decide almost everything: the last layer at 224 px gave 0.965 mean image AUROC, block 8 at 448 px gave 0.991, ahead of the classic WideResNet-50 PatchCore (0.985). Copying PatchCore's 3 × 3 pooling made DINOv3 worse.

The previous post built a Vision Transformer and loaded DINOv3’s weights into it. This post is about where those weights come from, and what to do with them.

DINOv3 (Meta, 2025) is a family of vision backbones trained by self-supervised learning: no labels, no captions, just 1.7 billion images and an objective that makes the network describe what it sees in a consistent way. The result is a general-purpose feature extractor. You keep it frozen, run it once per image, and put something small on top: a linear classifier, a nearest-neighbor search, a segmentation head, a detector.

I will explain how the training works, look at the features, go through the main ways people use them, and then spend the second half on one use case in depth: defect detection with a memory bank of normal patches, the “PatchCore” approach. It is popular in industrial inspection, it is easy to get almost right and still disappointing, and every design choice is measurable, so I measured them on all fifteen categories of MVTec AD.

All ViTs use 16-pixel patches, four register tokens and rotary position embeddings, exactly the architecture from the previous post. The ConvNeXt variants are for hardware where transformers are awkward. The weights are on Hugging Face under the DINOv3 license; you need to accept it on the model page before downloading. I use ViT-S/16 throughout, because it runs comfortably on a laptop; the defect-detection experiments ran on a desktop GPU only to save time.

Learning without labels

The difficulty of self-supervised learning is not finding a task; it is finding a task that cannot be solved by cheating. “Make the features of two crops of the same image similar” is solved trivially by outputting a constant. Everything in the DINO family is about making that shortcut impossible while keeping the task meaningful.

DINO: self-distillation across crops

From each training image, DINOv3 cuts two global crops (256 px, most of the image) and eight local crops (112 px, small parts). The student network sees all ten; the teacher sees only the two global ones. Both end in a head that turns the CLS token into scores over K “prototypes” (256k for the 7B model), and the student is trained so that its distribution over prototypes, from any crop, matches the teacher’s distribution from the global crops. A local crop of a dog’s ear has to produce the same answer as the whole dog. The only way to do that reliably is to recognize what is in the image.

Two mechanisms prevent the constant-output shortcut:

  • The teacher is an exponential moving average (EMA) of the student. It changes slowly and smoothly, which makes it a stable, slightly better target, a kind of ensemble of recent students.
  • The teacher’s outputs are balanced across prototypes. If one prototype won for every image, the targets would carry no information. DINOv2 and v3 enforce balance with a few Sinkhorn-Knopp iterations, which rescale the teacher’s scores so that every prototype receives the same total weight across the batch:
python
import torch
import torch.nn.functional as F


@torch.no_grad()
def sinkhorn_knopp(teacher_logits, temp=0.07, iters=3):
    """Turn teacher scores (B, K) into targets that use all K prototypes equally."""
    q = torch.exp((teacher_logits - teacher_logits.max()) / temp).T  # (K, B)
    q /= q.sum()
    k, b = q.shape
    for _ in range(iters):
        q /= q.sum(dim=1, keepdim=True) * k  # every prototype gets 1/K of the mass
        q /= q.sum(dim=0, keepdim=True) * b  # every image gets 1/B of the mass
    return (q * b).T  # (B, K), each row sums to 1


def dino_loss(student_logits, teacher_logits, student_temp=0.1):
    """Cross-entropy between balanced teacher targets and the student."""
    targets = sinkhorn_knopp(teacher_logits)
    log_p = F.log_softmax(student_logits / student_temp, dim=-1)
    return -(targets * log_p).sum(-1).mean()

On a toy batch of 64 images and 32 prototypes in which one prototype dominates, a plain softmax gives that prototype 16.3 of the 64 images’ worth of probability; after three Sinkhorn iterations it gets 2.1, close to the fair share of 2.

iBOT: predicting masked patches

The DINO loss only looks at one vector per crop, so it says nothing directly about the patch tokens. iBOT adds a patch-level task: some patches of the student’s global crops are replaced by a learned mask_token (the one the previous post’s code kept “for training only”), and the student must predict the teacher’s output for exactly those patches. The teacher sees the unmasked image. To succeed, a patch feature must encode what is in that patch, inferred from its surroundings. This is what gives DINO models their strong dense features.

A third, small term, the KoLeo regularizer, pushes the features of different images in a batch apart, so that they spread over the whole space instead of clustering:

python
def koleo(x, eps=1e-8):
    """Penalize each feature being close to its nearest neighbor in the batch."""
    x = F.normalize(x, dim=-1)
    d = torch.cdist(x, x)
    d.fill_diagonal_(float("inf"))
    return -torch.log(d.min(dim=1).values + eps).mean()

The total loss of the first training phase is ℒDINO+ℒiBOT+0.1ℒKoLeo.

Scaling up, and the problem of dense features

DINOv3’s main ingredients are scale and a fix for what scale broke.

Data. From a pool of about 17 billion public Instagram images, Meta built a curated set of 1.69 billion (LVD-1689M) by clustering DINOv2 embeddings hierarchically and sampling evenly from the clusters, so that rare concepts are as well represented as common ones. A retrieval-based subset close to standard benchmarks and ImageNet itself are mixed in; 10% of batches are pure ImageNet-1k.

Model and schedule. The teacher is a 40-block ViT with 4,096 channels and 6.7 billion parameters. Instead of cosine schedules that require knowing the training length in advance, it trains with constant learning rate, weight decay and EMA momentum for 1 million iterations, so training can continue as long as results improve.

The problem. As training went on, image-level results kept improving, but dense results got worse. After about 200k iterations, segmentation accuracy of a linear probe on the patch features started to fall, and similarity maps between a patch and the rest of the image became noisy: patches far from the object started to look similar to it. The paper traces this to the patch features becoming more and more similar to the CLS token, losing their locality.

The fix: Gram anchoring. The Gram matrix of an image is the P×P matrix of cosine similarities between all its patch features. A clean Gram matrix means “patches on the same object are similar, patches on different objects are not”. Gram anchoring adds a loss that keeps the student’s Gram matrix close to that of an earlier checkpoint, the Gram teacher, whose patch features were still clean:

ℒGram=‖XSXS⊤−XGXG⊤‖F2,

where XS and XG are the L2-normalized patch features of the student and of the Gram teacher.

python
def gram_loss(student_patches, gram_teacher_patches):
    """Match the patch-to-patch cosine similarity matrices of one image, (P, d) each."""
    s = F.normalize(student_patches, dim=-1)
    g = F.normalize(gram_teacher_patches, dim=-1)
    return ((s @ s.T - g @ g.T) ** 2).sum()

The elegant part is what this loss does not constrain. Rotate all patch features by the same orthogonal matrix, and the Gram matrix does not change: the loss is exactly zero (I checked: 4×10−11 in float32). The features are free to keep learning; only the structure of which patches resemble which is anchored. DINOv3 applies it after 1 million iterations, refreshes the Gram teacher every 10k iterations, and feeds the Gram teacher images at twice the resolution (then downsamples its features), which gives an even cleaner target. On ADE20k segmentation the high-resolution Gram teacher alone added about 2 mIoU.

Post-training. Three short phases finish the job: a high-resolution adaptation with crops up to 768 px (again with Gram anchoring), which makes the model usable at much higher resolutions than it was trained at; distillation of the 7B teacher into the smaller models listed above, several students at once; and, optionally, training a text encoder against the frozen ViT-L (“dino.txt”) for zero-shot classification.

Using a frozen DINOv3

Getting features out

With Hugging Face transformers, a forward pass gives you everything:

python
import numpy as np
import torch
import torch.nn.functional as F
from PIL import Image
from transformers import AutoModel

MEAN = torch.tensor([0.485, 0.456, 0.406])[:, None, None]
STD = torch.tensor([0.229, 0.224, 0.225])[:, None, None]


def preprocess(img, size=(448, 448)):
    """PIL image -> normalized (1, 3, H, W); both sides must be multiples of 16."""
    img = img.convert("RGB").resize(size, Image.BICUBIC)
    x = torch.from_numpy(np.array(img)).permute(2, 0, 1).float() / 255
    return ((x - MEAN) / STD)[None]


model = AutoModel.from_pretrained("facebook/dinov3-vits16-pretrain-lvd1689m").eval()
with torch.no_grad():
    out = model(pixel_values=preprocess(Image.open("photo.jpg")), output_hidden_states=True)

cls = out.pooler_output  # (1, 384): one vector for the whole image
patches = out.last_hidden_state[:, 5:]  # (1, 784, 384): skip CLS + 4 registers
grid = patches.unflatten(1, (28, 28))  # (1, 28, 28, 384): a feature map at stride 16
block6 = out.hidden_states[6][:, 5:]  # output of block 6 (before the final norm)

Four practical rules:

  • Normalize with the ImageNet mean and standard deviation, as shown. DINOv3 was trained that way.
  • Use side lengths that are multiples of 16. Anything left over is cut off silently.
  • Skip the first 5 tokens for patch features: they are the CLS token and the 4 registers. Forgetting this shifts every patch by five positions, a classic silent bug.
  • Choose the resolution for the smallest detail you care about. One patch covers 16 × 16 input pixels. If a scratch is 20 pixels wide in a 2,000-pixel photo resized to 448, it covers less than a third of a patch.

The common patterns

Almost every application of DINOv3 is one of these:

Goal Features On top
Image classification CLS (often concatenated with the mean patch) A linear layer or logistic regression
Retrieval, deduplication, clustering CLS, L2-normalized Cosine similarity, k-nearest neighbors, k-means
Few-shot classification CLS of a few labeled examples Nearest class prototype
Semantic segmentation Patch features A linear layer per patch, upsampled
Depth, surface normals Patch features (several layers) A small dense head (DPT)
Correspondence, tracking Patch features Nearest-neighbor matching between images or frames
Object detection Patch features through a simple pyramid A DETR-style decoder
Anomaly and defect detection Patch features of normal images A memory bank and nearest-neighbor distances
Zero-shot classification dino.txt text tower Image-text similarity

Two things stand out. First, most heads are tiny, often a single linear layer, because the features already carry the information. Second, the same backbone pass can serve several heads at once, which is the strongest argument for keeping it frozen: one feature extraction feeds the classifier, the retrieval index and the segmenter.

Frozen or fine-tuned? Keep it frozen when you have little labeled data, many tasks, or a deployment budget for one backbone pass. Fine-tune when one task matters most and you have enough labels; use a learning rate for the backbone about ten times smaller than for the head. The DINOv3 paper makes the case for frozen features at the top end: a frozen 7B backbone under a Plain-DETR decoder reached 66.1 mAP on COCO. For real-time detection, DEIMv2 uses DINOv3-pretrained or distilled backbones for its S to X models, with a small adapter that turns the single-scale ViT output into multi-scale features; DEIMv2-S reaches 50.9 AP on COCO with under 10 million parameters.

Deep dive: defect detection with a memory bank

The idea

In industrial inspection, defects are rare and varied. You may have thousands of good parts and a handful of scratched ones, and next month’s defect will look different from this month’s. So the most popular family of methods trains on normal images only and flags whatever does not look normal.

PatchCore (Roth et al., 2022) is the standard recipe, and it needs no training at all:

  1. Run every normal training image through a frozen backbone and keep every patch feature. This is the memory bank: for 200 images at 448 px, 200 × 28 × 28 = 156,800 vectors.
  2. For a test image, compute each patch’s distance to its nearest neighbor in the bank. A patch that resembles some normal patch gets a low score; a patch unlike anything seen before gets a high one.
  3. Upsample the patch scores to an anomaly map, smooth it, and take its maximum as the image score.

Every choice in this recipe matters: which backbone, which layer, which resolution, whether to pool neighboring patches, how to shrink the bank, how to turn a map into one number. When a memory bank “does not work very well”, one of these is usually the reason, and each can be measured.

The benchmark

MVTec AD (Bergmann et al., 2019) is the standard dataset: 15 categories of objects and textures, 3,629 normal training images, and 1,725 test images of which 1,258 contain defects such as scratches, cracks, holes, contamination and missing parts, each with a pixel-accurate mask. Two numbers are reported per category:

  • Image AUROC: how well the image score separates defective from good images. 1.0 means some threshold separates them perfectly; 0.5 is chance.
  • Pixel AUROC: the same question for every pixel, against the defect masks. It measures localization.

I computed both for every configuration below on all 15 categories with DINOv3 ViT-S/16, the smallest model in the family, on an RTX 3070 Ti. For comparison, I also ran the original PatchCore backbone, a WideResNet-50 pretrained on ImageNet with labels, using layers 2 and 3 as in the paper. Every number below comes from these runs; there is no coreset subsampling unless stated.

What I varied

Results

Four lessons, in order of how much they matter.

Resolution first. Going from 224 to 448 pixels lifts the last layer from 0.965 to 0.989 image AUROC. At 224, one patch covers 1/14 of the image side; a thin scratch or a damaged screw thread is a small fraction of one patch, and its signal is averaged away with the surrounding normal texture. The worst category, screw, goes from 0.796 to 0.894.

Then the layer. The last layer is the wrong place to look for defects. DINO’s training objective asks two crops of an image, with different color jitter, blur and solarization, to produce the same output, so the last layers learn to ignore exactly the low-level changes that many defects consist of. Intermediate blocks still carry them. Block 8 at 448 px is the best simple configuration (block 10 is as good), 0.991 image AUROC and 0.983 pixel AUROC, ahead of the classic WideResNet-50 PatchCore (0.985 and 0.980). The difference shows most in localization on textures, where the pixel AUROC for the five texture categories rises from 0.958 (last layer) to 0.988.

Do not copy the CNN recipe blindly. PatchCore averages each patch with its neighbors because a CNN feature at layer 2 or 3 sees only a small region; pooling adds context. A ViT patch already attends to the whole image in every block. On DINOv3, pooling hurt the image AUROC every time: the last layer drops from 0.989 to 0.977, and the full PatchCore recipe (blocks 6 + 8, pooled) reaches only 0.980. Pooling block 8 alone does the same: 0.991 drops to 0.980.

The rest matters little. Cosine distance instead of Euclidean was slightly worse for both layers I tried (block 8: 0.988 against 0.991). Taking the mean of the top 1% of the map instead of its maximum changed little (0.986 against 0.989). A greedy coreset, which keeps the points that cover the bank best, cost almost nothing: keeping 10% of the bank gave the same result as the full bank (0.992 against 0.991), and keeping 1% lost 0.002 image AUROC and 0.005 pixel AUROC. That is PatchCore’s main trick for speed, and it transfers.

Blocks 8 and 10 are equally good. Block 4 is too low-level: it describes edges and local texture, so on objects every change of pose already looks anomalous (0.957 on the ten object categories, against 0.982 on textures). And on MVTec AD, resolution saturates at 448 px. 672 and 896 px mean 2.25 and 4 times as many patches, for both the backbone and the bank, without improving the averages. The exception is telling: screw, the category with the smallest defects, keeps improving up to 896 px (block 8: 0.961, 0.965, 0.968). Choose the resolution from the size of your smallest defect, not from a benchmark average. For MVTec’s defects, 28 patches across are enough; for a hairline crack in a 4K image of a large part, they will not be.

Two categories deserve a comment. Screw is hard for every method because screws lie at random angles and the defects (a damaged thread tip) are tiny; it is the category that improves most with resolution and layer choice, from 0.796 to 0.961. Transistor goes the other way: the PatchCore baseline is perfect, and block 8 is the weakest of the good configurations (0.976), while the last layer at 448 px reaches 0.993. Its defects include misplaced and missing transistors, which are not unusual textures but unusual arrangements: every patch looks like some normal patch, only in the wrong place. That calls for more global, more semantic features. No single layer is best for every kind of defect.

What the maps look like

Switch between the two settings and two patterns appear. The naive maps are blurry: at 224 px one patch is 1/14 of the image side, so the carpet’s hole lights up a region many times its size and the grid’s bent wires glow as wide halos. At block 8 and 448 px the orange sits on the defects themselves: the bent wires, the hole, the scratch on the metal nut. And small defects stay hard. The damaged tip of the screw barely rises above a normal screw in either setting, and with block 8 the strongest spot is on the shaft, not at the tip. One image per category is an anecdote; the AUROC numbers above, over all 1,725 test images, are the evidence.

How many normal images do you need?

A memory bank needs no training, so the only question is how much normal data it needs. I rebuilt the bank (block 8, 448 px) from 1, 4 or 16 randomly chosen good images, three random draws each, and averaged:

The split is by kind of variation, not by difficulty. For textures (carpet, leather, tile, grid) and objects that look much the same in every image (bottle, metal nut, toothbrush), a single good image is enough: its patches already cover what normal looks like. Objects that appear in different poses need the bank to contain those poses. Hazelnuts lie at random angles and need about 16 images; screws also lie at random angles and their defects are tiny, and with one image the detector is at chance (0.476). For a new inspection task, this suggests starting with a handful of good images, measuring, and spending further collection effort on the variation that is missing rather than on more of the same.

A memory bank in 40 lines

Here is the whole method on top of the Hugging Face model, with the best configuration from above as the default:

python
import torch
import torch.nn.functional as F
from torchvision.transforms.functional import gaussian_blur


class MemoryBank:
    """PatchCore-style defect detection on frozen DINOv3 patch features."""

    def __init__(self, model, layers=(8,), side=448, pool=False):
        self.model, self.layers, self.side, self.pool = model, layers, side, pool

    @torch.no_grad()
    def features(self, images):  # list of PIL images -> (N, h, w, C)
        x = torch.cat([preprocess(im, (self.side, self.side)) for im in images])
        out = self.model(pixel_values=x, output_hidden_states=True)
        h = w = self.side // 16
        # hidden_states[i] is the output of block i; drop CLS + 4 registers
        f = torch.cat([out.hidden_states[i][:, 5:] for i in self.layers], dim=-1)
        f = f.unflatten(1, (h, w))
        if self.pool:  # average each patch with its 8 neighbors
            f = F.avg_pool2d(f.permute(0, 3, 1, 2), 3, 1, 1).permute(0, 2, 3, 1)
        return f

    def fit(self, normal_images, batch=8):
        feats = [
            self.features(normal_images[i : i + batch])
            for i in range(0, len(normal_images), batch)
        ]
        self.bank = torch.cat(feats).flatten(0, 2)  # every patch of every normal image
        return self

    @torch.no_grad()
    def score(self, images, out_size=256):
        f = self.features(images)
        n, h, w, c = f.shape
        d = torch.cdist(f.reshape(-1, c), self.bank).min(dim=1).values  # nearest normal patch
        maps = F.interpolate(d.view(n, 1, h, w), size=out_size, mode="bilinear")
        maps = gaussian_blur(maps, kernel_size=33, sigma=4.0)[:, 0]
        return maps, maps.flatten(1).amax(dim=1)  # anomaly maps, image scores

preprocess is the function from the feature-extraction example. Use it like this:

python
from pathlib import Path

goods = [Image.open(p) for p in sorted(Path("toothbrush/train/good").glob("*.png"))]
bank = MemoryBank(model).fit(goods)
maps, scores = bank.score([Image.open("toothbrush/test/defective/000.png")])

Run on all 42 toothbrush test images, this class gives an image AUROC of 0.992 and a pixel AUROC of 0.995, the same as the experiment code, in 35 seconds on a laptop CPU. For large banks, replace torch.cdist with a chunked search or a library such as FAISS, and subsample the bank with a coreset.

Why your memory bank may have disappointed

If you have built one of these and it did not work very well, here is a checklist, roughly in order of how often each problem occurs:

  1. The input was 224 px. The single biggest effect in my measurements. Resize to 448 or more, and check that the smallest defect you care about covers at least one 16-pixel patch at that resolution. With RoPE, DINOv3 runs at any multiple of 16, and rectangular inputs work too.
  2. The features came from the last layer or the CLS token. Use intermediate blocks (block 8 of 12 for ViT-S; for bigger models, start around two thirds of the depth). The CLS token cannot localize, and it was the weakest option for detection too (0.956).
  3. A CNN recipe was applied to a ViT. 3 × 3 pooling and layer concatenation are tuned for ResNets. Measure them; on DINOv3 they made things worse.
  4. The bank did not cover normal variation. This is the main failure in production, and MVTec hides it, because its normal images are carefully controlled. If parts arrive at different angles, under different lighting, or from a new supplier, every unfamiliar-but-good patch scores high. Put that variation into the bank: more good images from different days and batches, rotated or flipped copies when the part allows it, or align the parts before scoring.
  5. The threshold was guessed. AUROC does not need a threshold; production does. Hold out a set of good images, score them, and set the threshold from their distribution, for example just above their maximum. Figure 6 uses a related reference, the peak of a typical good image.
  6. The bank was contaminated. One defective image in the “good” set teaches the bank that this defect is normal, and similar defects will score low later. Inspect the images with the highest scores within the training set; they are either unusual good parts or mislabeled defects.
  7. The defect is logical, not visual. A missing component or a wrong arrangement can be made entirely of normal-looking patches, as the transistor results show. Combine a mid-level layer with a deeper one, or add a global check.

And one strategic point. A memory bank is the right tool when defects are rare, varied or unknown. Once you have collected a few hundred labeled examples of the defects that actually occur, a supervised detector or segmenter trained on them, a YOLO model for example, will usually beat it on those defects. The two work well together: the memory bank finds candidates, a person confirms them, and the confirmed defects become training data for the detector. The next post shows how SAM 3 turns such a candidate into a clean mask with one click.

Cheat sheet

Concept In one line
Self-supervised learning Learn features from unlabeled images by making different views agree
DINO loss From any crop, the student matches the teacher’s distribution over prototypes for the global crops
iBOT loss The same for masked patches: predict the teacher’s view of what is under the mask
KoLeo A spreading term that keeps features from collapsing onto each other
Teacher An exponential moving average of the student; never trained by gradients
Gram anchoring Keep the patch-to-patch similarity matrix close to an earlier checkpoint; fixes dense features at scale
Using it Freeze, extract CLS or patch features once, put a small head or a nearest-neighbor search on top
Patch tokens last_hidden_state[:, 5:]: skip CLS and the 4 registers
Memory bank Nearest-neighbor distance from each test patch to the patches of normal images
Best bank settings (ViT-S) Block 8, 448 px or more, no pooling, full bank or a 10% coreset
Common mistakes 224 px, last layer, CLS token, CNN-style pooling, a guessed threshold, a bank without real normal variation

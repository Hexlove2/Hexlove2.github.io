Key takeaways

  1. A count is a sum over thousands of frames, so its errors come from three places: the detector (misses, duplicates, and what counts as one object), the rule that decides which frame or track owns an object, and the system (dropped frames, speed changes). Measure each one separately.
  2. For stitched line-scan images, assigning each object to the frame that contains its box center is sound as long as both frames see the whole object. On a real corn-kernel stream with 200 px of context, the two views placed the center within 0.12 px of each other on average, and 1 of 714 boundary cases was counted twice. With only 25 px of context, the center rule double-counted 24.
  3. Letting the earlier window decide (skip anything the previous window already counted, matched by intersection over the smaller box) removed every boundary error with 25 px of context or more, and gives identical counts where nothing is ambiguous.
  4. Tracking-based counting breaks when objects move too far between frames. With 60 px kernels, ByteTrack and BoT-SORT counted 120 of 120 at 16 px per frame, 69 at 32 and 18 at 40, because a new track needs overlapping boxes in its first two frames. A tracker that predicts with the known belt speed counted correctly at every speed up to 96 px per frame.

“Count the objects” sounds like len(detections). On a production line it is a different problem. A bag of seed corn is counted kernel by kernel as it pours past a camera; a packaging line counts parts as they ride by on a belt. The count is a sum over thousands of frames, the customer cares about the error of the total, and an error of 0.5% can be the difference between a working machine and a complaint.

This post is about everything between the detector and that total. It has two parts, for the two situations I meet most often:

  1. A line-scan camera, where the image is built row by row as objects move past, and every object appears in exactly one stretch of the stream. The problem is the frame boundaries. I use a real project for this: counting corn kernels with a YOLO11s model on a 2048-pixel line-scan camera.
  2. An area camera over a conveyor, where each object appears in many consecutive frames. Counting needs tracking, and tracking has its own ways to fail.

Everything is measured. The line-scan part uses the real model and real images from the corn project; the conveyor part uses the same model on a synthetic belt built from real kernel images, so that the true count is known exactly.

Where counting errors come from

Before any algorithm, it helps to name the error sources, because they need different fixes:

Source Example How to see it
The detector a kernel missed in a cluster, two boxes on one kernel, a fragment counted as a kernel check frames by hand; precision and recall on labeled frames
The ownership rule an object at a frame boundary counted by both frames, or by neither; a track broken in two compare overlapping views, or tracks against ground truth
The system a dropped frame, a belt that speeds up, a camera trigger that skips frame numbers, encoder counts, timing logs

Errors of the second kind are the ones people worry about, because they feel systematic. As we will see, on a well-designed line-scan setup they are the smallest of the three; on a conveyor with tracking they can be the largest.

Two further habits make the rest easier. Measure the count error per batch (counted minus true, on batches you have counted by hand), not only detection mAP: a detector with 99% recall can still give a biased count. And keep in mind that errors of opposite sign cancel. A total that comes out right can hide a miss and a double count; in one of the experiments below, that is exactly what happened.

Part 1: line-scan cameras

How a line-scan camera sees

A line-scan camera has a single row of pixels, here 2,048 of them. It takes thousands of exposures per second while the material moves past, and stacks the rows into an image. There are no frames in the physical sense: the camera delivers a continuous strip, and the software cuts it into chunks for processing, in this project 1,200 rows each.

Two properties follow:

  • The geometry is known exactly. The material moves through the line, so frame k+1 continues exactly where frame k ended. Nothing appears twice, and nothing moves sideways. (To keep the scale constant, the line rate is tied to the transport speed: line rate = speed / size of one pixel on the object. Systems with varying speed trigger each line from an encoder.)
  • Objects are cut at frame borders. A kernel that passes the line while frame k ends is split between two frames. Count each frame separately and that kernel is seen as two halves, or not at all.

Stitching and a counting band

The corn system solves the second problem by stitching. Before detection, the last 400 rows of the previous frame are stacked on top of the current frame, so the model sees a 2048 × 1600 window. A kernel cut by the frame border is complete in this window. But now every kernel near a border is seen twice, once in each of two consecutive windows, so a rule must decide which window counts it.

The rule is a counting band: rows 200 to 1,400 of each window. A window counts a kernel if the center of its box lies in the band. The bands of consecutive windows touch exactly (the band of the next window starts at row 200 of that window, which is row 1,400 of this one), so every row of the strip belongs to exactly one band, and every kernel should be counted exactly once. Each band boundary has 200 rows of context on either side, more than the largest kernel (113 px tall in the samples, median 61 px).

Is the center rule ambiguous?

The obvious worry: a kernel whose center lies near the band boundary is detected in both windows, and the two detections are not identical. If the upper window puts its center 1 px above the line and the lower window 1 px below it, both count it. If they disagree the other way, neither does. So the question is how much the two views disagree.

I measured it. Three of the sample frames turned out to be consecutive (each starts with the last 400 rows of the previous one), which gives a continuous strip of 4,000 rows. On this strip I moved a virtual boundary line in 10-row steps and, for each position, cut out the two windows that meet there, exactly as the production code does, and ran the model on both.

The result is reassuring. Over 121 boundary positions, kernels near the line appeared 1,093 times in both windows, 220 of them with the box straddling the line. The box centers in the two views differed by 0.12 px on average (at most 0.6 px), and every pair of boxes overlapped with an IoU of at least 0.975. Not a single kernel was counted twice or missed.

The reason is the context. With 200 rows on each side, both windows see the whole kernel and its surroundings, the model produces almost the same box, and the center can only land on different sides of the line if it is within a fraction of a pixel of it. That does happen: in a second run of the experiment, one kernel’s center lay 0.1 px above the line in one window and 0.1 px below it in the other, and it was counted twice. It is just rare: for a line to fall between two centers a tenth of a pixel apart, a kernel must sit almost exactly on it.

When the center rule fails

The failure appears when there is too little context. I repeated the experiment with less and less context on each side of the line, from 200 px down to none, and compared every kernel within 150 px of the line against a reference window that saw it completely:

Context on each side Center rule Earlier window decides
0 px (no stitching) 86 missed 86 missed
10 px 39 missed 39 missed
25 px 24 counted twice 0
50 px 2 counted twice 0
100 to 200 px 1 counted twice 0

Two different mechanisms are at work.

  • Without context, kernels are missed. With no overlap at all, a kernel cut by the border appears as two partial kernels, and the model, trained on whole kernels, detects neither half with enough confidence. That is 12% of the kernels near a border: the reason stitching exists in the first place.
  • With a little context, kernels are counted twice. At 25 px, a window sees a kernel that crosses its edge only partially. The box of the visible part is shorter, so its center moves toward the window’s own side of the line, and both windows claim the kernel.

A fix: let the earlier window decide

The center rule makes two independent decisions about the same kernel, one in each window, and they can disagree. The fix is to make only one decision. The earlier window decides with the center rule as before and hands on a list of the boxes it counted. The next window checks each of its own boxes against that list: if a box overlaps one on the list, it is the same kernel, already counted, and is skipped; everything else above its lower line is counted. A kernel’s fate is settled by the first window that decides about it, and no later window can contradict that.

The video shows both rules on the same real detections: first with only 25 px of context, where truncated boxes put two kernels’ centers on opposite sides of the line, then with the production setting of 200 px and the one kernel in the experiment that sat 0.1 px from the line:

In code, the whole rule is a list and an overlap test:

python
import numpy as np

STEP = 1200  # new rows per frame: a stitched window is 400 old rows + 1,200 new rows
LINE = 1400  # lower edge of the counting band, in window coordinates


def ios(a, b):
    """Intersection over the smaller box, for boxes a (n, 4) and b (m, 4)."""
    x1 = np.maximum(a[:, None, 0], b[None, :, 0])
    y1 = np.maximum(a[:, None, 1], b[None, :, 1])
    x2 = np.minimum(a[:, None, 2], b[None, :, 2])
    y2 = np.minimum(a[:, None, 3], b[None, :, 3])
    inter = np.clip(x2 - x1, 0, None) * np.clip(y2 - y1, 0, None)
    area = lambda r: (r[:, 2] - r[:, 0]) * (r[:, 3] - r[:, 1])  # noqa: E731
    return inter / np.minimum(area(a)[:, None], area(b)[None])


def count_window(boxes, prev_counted, thr=0.5):
    """Boxes to count in this stitched window; the earlier window's decision wins.

    boxes: (n, 4) x1, y1, x2, y2 detected in this window.
    prev_counted: what count_window returned for the previous window.
    Returns the counted boxes; pass them in again with the next window.
    """
    boxes = np.asarray(boxes, dtype=float).reshape(-1, 4)
    mine = boxes[(boxes[:, 1] + boxes[:, 3]) / 2 < LINE]  # everything above the lower line
    prev = np.asarray(prev_counted, dtype=float).reshape(-1, 4) - [0, STEP, 0, STEP]
    if len(mine) and len(prev):
        mine = mine[ios(mine, prev).max(axis=1) < thr]  # skip kernels the previous window counted
    return mine

Three details make it robust:

  • Intersection over the smaller box (IoS) instead of IoU. A kernel truncated at the window edge has a small box inside the full box of the other view; their IoU is low, but the IoS is close to 1. The SAHI library, which merges detections from overlapping image tiles, uses the same measure with the same threshold of 0.5 by default.
  • The earlier window’s decision is final. If the earlier window counted the kernel, the later one skips it; if the earlier window did not count it, because its center was below the line or because it was not detected at all, the later one counts it. A kernel the earlier window missed gets a second chance.
  • Nothing else changes. On the three real stitched windows, it gives the same per-window counts as the center rule (51, 36 and 48), and on the 714 boundary cases of the experiment, under the production geometry, it misses none and counts none twice. It also makes the first frame consistent with the rest: the production code counts the first window with a different rule, and a kernel whose box crosses that window’s lower line but whose center is above it is counted by neither the first nor the second window. With count_window, the first window simply has nothing to defer to.

This is the line-scan version of an idea that will come back in part 2: decide once per object, not once per view. Because the motion between windows is known exactly (1,200 rows), recognizing the same kernel in two windows needs no tracker, just a coordinate shift and an overlap test.

What actually limits the count

With 200 px of context, the boundary rule contributes about one error per 700 kernels near boundaries, and with the fix, none in this data. The count is limited elsewhere.

What counts as one kernel. Of the 1,295 boxes the model produced on the twelve sample windows with a confidence of at least 0.05, 1,247 had a confidence above 0.9 and only 16 fell below the threshold of 0.6. Those are instructive:

Should a broken half kernel be counted? It depends on what the customer counts, and the labels must follow that decision consistently. A model trained on inconsistent labels for fragments will flicker around the threshold exactly on these objects. Write the definition down, label a set of fragments deliberately, and check the confidence distribution: a healthy counting model, like this one, puts almost nothing between 0.2 and 0.8 (here 17 of 1,295 boxes).

Touching kernels and duplicates. Clusters are where detectors miss objects or put one box over two. The model here separates touching kernels well (Figure 2), and the low-confidence boxes spanning two kernels are rejected by the threshold. For denser material, keep the NMS IoU threshold high (production uses 0.7) so that two genuinely overlapping kernels are not merged into one box, and look at the worst clusters by hand.

Dropped frames. With a line-scan camera, a lost frame is 1,200 rows of material that is never seen: every kernel in it is missed, and the next window is stitched to the wrong predecessor. This is the largest error a single event can cause, so it must be detected, not hoped away. The camera’s frame counter makes gaps visible (the corn system logs them); a counting system should treat a gap as a fault and report it, not continue silently.

Verify the whole chain. Run batches of known size (hand-counted, or weighed and converted) through the machine and report the mean and spread of the count error. That number, not mAP, is what the customer buys.

Part 2: counting by tracking on a conveyor

With an area camera over a belt, every object appears in many frames: a part that takes one second to cross the image at 30 frames per second is detected 30 times. To count it once, the system must know that those 30 detections belong to the same object. That is multi-object tracking.

How tracking by detection works

Almost every tracker used in production follows the same loop, introduced by SORT (Bewley et al., 2016). Each track is an object the tracker believes in, with a state (position, size, velocity) and an ID. For every new frame:

  1. Predict. Move every track forward with its motion model, usually a Kalman filter with constant velocity.
  2. Associate. Compare the predictions with the new detections, usually by IoU, and solve the assignment with the Hungarian algorithm: each detection to at most one track, maximizing the total overlap. Pairs below a threshold are not matched.
  3. Update. Matched tracks correct their state with the detection. Unmatched detections start new tracks. Tracks that stay unmatched for too many frames are deleted.

The variants differ in how they handle the hard cases:

Tracker Year What it adds Relevance on a conveyor
SORT 2016 The template: Kalman filter, IoU, Hungarian matching Works when objects move little between frames
DeepSORT 2017 An appearance descriptor (a re-identification network) to recover objects after occlusion Weak when all objects look alike: kernels, bottles, screws
ByteTrack 2021 A second matching round with low-confidence detections, so tracks survive blur and partial occlusion One of the two trackers in Ultralytics; robust to missed detections
OC-SORT 2022 Corrects the Kalman state after an occlusion using the observations instead of the drifting prediction Long occlusions, nonlinear motion
BoT-SORT 2022 ByteTrack plus camera-motion compensation, a better box state, optional appearance The Ultralytics default; the camera-motion part is unnecessary with a fixed camera

Counting with tracks

With tracks, there are three common ways to count:

  • Unique IDs: count how many track IDs were created. Simple, and fragile: every time a track breaks and restarts, the object is counted again.
  • Line crossing: count a track when its center crosses a line, once per ID. A track that breaks before or after the line still counts once, so this is far more robust. Compare positions with the last time the track was seen, not with the previous frame, so that a track that was lost for a few frames is still counted.
  • Zones: count when a track enters a region, useful when objects may stop or turn around.

For a belt moving in one direction, line crossing is the standard choice. Put the line where detection is easiest: away from the image edges, where objects are only partly visible, and away from anything that can hide them.

Orange boxes are IDs born in the last 15 frames: when a box on an object that has been visible for a while turns orange, its track just broke.

Three experiments worth trying: raise the speed above about 25 px per frame with the constant-velocity tracker and watch new IDs appear on every object; set the misses to 40% and compare nearest-center with the others; turn on the occluder at a low speed and watch tracks die behind it.

Measured: the speed cliff

To see the same effects with real detections, I built a synthetic belt: 120 real kernel images (cut out of the line-scan samples with transparent backgrounds), moving from left to right at a known speed, about 15% of them in touching pairs. The same belt layout was rendered at nine speeds, from 4 to 96 px per frame. The corn model detected every frame once, and four trackers ran on the same detections and counted kernels crossing the center line:

Up to 16 px per frame, every tracker counts 120 or 121. Between 24 and 40 px per frame, ByteTrack and BoT-SORT collapse: 112, then 69, then 18. The video shows why:

The cause is in how a track is born. A new detection starts a track with zero velocity, and the track is only confirmed (and reported) if the next frame contains a detection that overlaps its first box with an IoU of at least 0.3. For two equal boxes of width w shifted sideways by d,

IoU=w−dw+d≥0.3⟺d≤0.54w.

With jitter, smaller kernels and vertical offsets, the practical limit is lower: here, the count started to drop at 24 px per frame, 40% of the typical kernel width. Above the limit, tracks are born and immediately discarded in every frame, and nothing is ever counted. The nearest-centroid tracker degrades more gently but creates thousands of spurious IDs.

The rule of thumb for IoU-based trackers: objects should move less than about a third of their own width between frames. If they move faster, either reduce the motion per frame (a higher frame rate, or a camera that sees more of the belt so each pixel covers more distance), or give the tracker the motion.

Use what you know: the belt speed

On a conveyor, the motion is not unknown. The belt moves in one direction at a speed that an encoder can report, or that the tracks themselves reveal. A tracker that uses it does not need overlapping boxes:

python
import numpy as np
from scipy.optimize import linear_sum_assignment


def run_belt(frames, v, max_age=15, conf=0.25):
    """Track boxes on a belt moving right at v px/frame; frames: per-frame (n, 5) x1, y1, x2, y2, conf."""
    tracks, nid, out = {}, 0, []
    for t, d in enumerate(frames):
        d = np.array(d).reshape(-1, 5)
        d = d[d[:, 4] >= conf]
        ids = list(tracks)
        cur, used = [], set()
        if ids and len(d):
            # predict: last seen box shifted by the belt speed
            P = np.array([tracks[i]["box"] + np.array([1, 0, 1, 0]) * v * (t - tracks[i]["seen"]) for i in ids])
            # compare the left or the right edge, whichever is not clipped by the image border
            dx = np.minimum(np.abs(d[:, None, 0] - P[None, :, 0]), np.abs(d[:, None, 2] - P[None, :, 2]))
            dy = np.abs((d[:, None, 1] + d[:, None, 3]) / 2 - (P[None, :, 1] + P[None, :, 3]) / 2)
            cost = dx + dy
            gate = 0.4 * np.maximum(d[:, None, 3] - d[:, None, 1], P[None, :, 3] - P[None, :, 1])
            r, k = linear_sum_assignment(np.where(cost <= gate, cost, 1e6))
            for di, ti in zip(r, k):
                if cost[di, ti] <= gate[di, ti]:
                    cur.append((ids[ti], di))
                    used.add(di)
        for tid, di in cur:
            tracks[tid] = {"box": d[di, :4].copy(), "seen": t}
        for di in range(len(d)):
            if di not in used:  # unmatched detection: a new object
                tracks[nid] = {"box": d[di, :4].copy(), "seen": t}
                cur.append((nid, di))
                nid += 1
        tracks = {k: v_ for k, v_ in tracks.items() if t - v_["seen"] <= max_age}
        out.append([[tid, *map(float, d[di, :4])] for tid, di in cur])
    return out

It counted 121 of 120 at every speed from 4 to 96 px per frame, the extra one being a kernel on which the detector placed two boxes. One detail took a debugging round to find: while an object enters the image its box is clipped, and the center of a clipped box moves at half the belt speed. Predicting the center created a new ID for almost every kernel at the image edge; comparing the edge that is not clipped fixed it.

The general lesson is the same as in part 1: the more of the geometry you know, the less the tracker has to guess. A belt-speed prior turns association into a near-trivial matching problem, and it works even when the frame rate cannot keep up.

Missed detections and occlusion

At a moderate 16 px per frame, I dropped a random share of the detections to simulate a weaker detector or glare:

Detections dropped ByteTrack BoT-SORT Nearest centroid Belt-speed prior
10% 120 (7 extra IDs) 120 (9) 118 (96) 121 (2)
20% 120 (18) 120 (28) 114 (173) 121 (3)
30% 120 (25) 120 (35) 105 (381) 121 (4)
50% 116 (118) 118 (129) 72 (808) 121 (2)

Count at the line, out of 120, with the number of extra track IDs (fragments) in parentheses.

The Kalman-based trackers keep the count right even when a third of the detections are missing, but their tracks fragment: every extra ID is a track that broke and restarted. Counted by unique IDs instead of line crossing, ByteTrack would have reported 171 kernels at 30% dropout.

Occlusion is the same problem in a block. I removed every detection between x = 560 and 720 px, as if a bracket covered that part of the belt, and placed the counting line either inside that region or after it:

Belt speed Frames hidden Line inside the occluded region Line after it
4 px/frame 40 ByteTrack 0, belt prior 0 ByteTrack 120, belt prior 121
8 px/frame 20 ByteTrack 120, belt prior 0 ByteTrack 120, belt prior 121
16 px/frame 10 ByteTrack 120, belt prior 121 ByteTrack 120, belt prior 121

When a track survives the occlusion (ByteTrack keeps lost tracks for 30 frames, my belt tracker for 15), the crossing is detected by comparing the position before and after the gap. When the occlusion lasts longer than that, the track dies, a new one is born on the far side of the line, and the kernel is never counted. Two rules follow: keep tracks alive longer than the longest occlusion, measured in frames at the slowest belt speed, and never put the counting line where objects can be hidden.

Configuring Ultralytics for a conveyor

With Ultralytics, the tracker is a YAML file. For a belt with occasional occlusions, a copy of bytetrack.yaml with a longer buffer is a reasonable start:

yaml
tracker_type: bytetrack
track_high_thresh: 0.25
track_low_thresh: 0.1
new_track_thresh: 0.25
track_buffer: 60
match_thresh: 0.8
fuse_score: True

and counting by line crossing takes a dozen lines:

python
from ultralytics import YOLO

model = YOLO("best.pt")
LINE_X = 640
last_x, counted = {}, set()
for frame in frames:
    r = model.track(frame, persist=True, tracker="conveyor.yaml", imgsz=608, conf=0.1, verbose=False)[0]
    if r.boxes.id is None:
        continue
    for tid, (x1, y1, x2, y2) in zip(r.boxes.id.int().tolist(), r.boxes.xyxy.tolist()):
        cx = (x1 + x2) / 2
        if last_x.get(tid, cx) < LINE_X <= cx:
            counted.add(tid)  # crossed the line from left to right since we last saw it
        last_x[tid] = cx

Pass a low conf so that ByteTrack’s second matching round receives the low-confidence boxes it is designed to use; the tracker’s own thresholds decide what starts a track. And check the belt speed against the frame rate before trusting the result: at more than a third of an object width per frame, use a belt-speed prior instead.

A checklist

Line-scan counting

  • Overlap consecutive frames by at least the largest object plus a margin on each side of the boundary (here 200 px for kernels up to 113 px).
  • Make one decision per object: let the earlier window decide, matching by intersection over the smaller box.
  • Use the same rule for the first frame as for all others.
  • Treat frame-number gaps as faults.

Conveyor counting by tracking

  • Keep the motion per frame below about a third of the object width, or use the belt speed in the tracker.
  • Count by line crossing, comparing with the last seen position; place the line away from image edges and occluders.
  • Keep lost tracks longer than the longest occlusion, in frames at the slowest speed.
  • Feed the tracker low-confidence detections when using ByteTrack.

Both

  • Define what counts as one object (fragments, clusters) and label accordingly.
  • Measure the count error on hand-counted batches, and look at the individual errors: right totals can hide cancelling mistakes.
